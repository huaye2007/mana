## 1. 测了什么，结论能外推多远

这是 game-data 第一次对真实数据库做压测。在此之前仓库里没有任何 Data 基准：game-benchmark 只有 Metadata、
RouteExecutor 与 RpcWire，而且并不依赖 game-data；[缺口分析](2026-10-17-framework-gap-analysis.zh-CN.md)
§3.1 与 §3.2 是从源码推理出来的，没有实测数据。

§2 与 §3 背后的压测代码写在临时目录里。此后它已在仓库中重建为
[DataSavePathLoad](../../game-benchmark/src/main/java/cn/managame/benchmark/DataSavePathLoad.java)，这些测量
因此可以重跑，而不只是被引用：

```shell
mvn -pl game-benchmark -am package -DskipTests
java -Xmx2g -cp game-benchmark/target/benchmarks.jar cn.managame.benchmark.DataSavePathLoad \
  "--url=jdbc:mysql://127.0.0.1:3306/ogbs_bench?rewriteBatchedStatements=true" --user=root --password=secret
```

它需要一个可丢弃的库：它会删除并重建 `bench_players`，并在该库还有任何其他表时拒绝启动。不给 `--url`（或
`OGBS_BENCH_MYSQL_URL`）时它只打印选项说明、什么都不做，也没有任何构建会运行它。选项以及它为何是 main 类而不是
JMH 基准，见[模块 README](../../game-benchmark/README.zh-CN.md#data-保存路径压测)。
[§5](#5-committed-harness-rerun) 是它自己在同一台机器、同一个 MySQL 上的运行结果，与下面的数字并列；两者不一致之处由
§5 说明，并且 §5 才是任何人都能重复的那一份。可外推的是比值，绝对速率只是某一台机器在 loopback 上的上限。

## 2. 不限速的生产在几秒内耗尽堆

`flushInterval=1s`、`batchSize=2000`、生产者不限速时，进程在 **7 秒**内因堆耗尽退出：

| 读数 | 值 |
| --- | --- |
| 结束时的 `DataStats.pendingChanges()` | 8,079,251 |
| 堆 | 806 MB → 2045 MB |
| `DataStats.flushes()` | **全程为 0** |

数据库全程健康，没有任何失败与重试。脏集合根本没有上限，于是超过排空能力的生产直接变成堆占用。`flushes()`
始终为 0 是另一半原因：一轮 pass 认领整个脏集合，所以那一轮正在跑的 pass，工作量由生产者而不是由管线决定，
运行期间从外部看不到任何进展。

同一套环境下限速运行完全稳定，这把问题定位在"生产快于排空"，而不是数据库或 Mapper 的任何地方：

| 生产速率 | `pendingChanges()` | 20 秒内的轮数 | 堆 |
| --- | --- | --- | --- |
| 30,000/s | 400~1,500，不增长 | 19 | 约 200 MB |
| 60,000/s | 400~1,500，不增长 | 19 | 约 200 MB |
| 不限速 | 8,079,251 且持续增长 | 0 | 2045 MB，随后 OOM |

[§5](#5-committed-harness-rerun) 重跑了这几个速率。上面两行限速数据是首轮最弱的部分，但原因不是 §5 早先一稿所
写的那个。它们的 flushInterval 就是 1 秒——20 秒 19 轮已经说明了这一点——而 §5.2 显示 1 秒间隔下 30,000/s 会留下
约 15,000 条等待，而不是 400~1,500。这组偏低的数字是采样假象：监控线程在一个与保存循环同时启动的循环里每次睡
一秒，于是每次采样都落在一轮 pass 刚结束之后、读到的是谷底，分布从未被观察到。这两行能支撑的结论是脏集合没有
增长；它们的量级不可信。

## 3. 吞吐上限

| 配置 | 行/秒 |
| --- | --- |
| INSERT，batchSize 500 | 47,000 |
| INSERT，batchSize 2000 | 77,000 |
| UPDATE，batchSize 500 | 16,700 |
| UPDATE，batchSize 2000 | 10,800 |

[§5.1](#51-吞吐) 重新测了这四项，连带修正了本节两处数字：该参数对 INSERT 的倍数并不是一个固定值，而是随
batchSize 增大；连接池的价值随配置从百分之几到约 90% 不等，本节的 28% 落在这个区间之内，而不是之外。

JDBC URL 上的 `rewriteBatchedStatements=true` 对 INSERT 值 **3.8 倍**（10,000 → 38,500 行/秒），对 UPDATE
只有 **1.7 倍**。不对称来自驱动：一批 INSERT 会被改写成一条多行 `VALUES`，而 `UPDATE … WHERE id=?` 无法折叠成
单条语句，每行仍是一次往返。同样的原因使更大的批次有利于 INSERT、不利于 UPDATE，所以一个 batchSize 不可能对两
边都最优。每批次新开连接而不用连接池约损失 28%：部署时值得修，但不是瓶颈。

## 4. 由此改了什么

| 发现 | 落点 |
| --- | --- |
| 一轮 pass 认领整个脏集合 | `PendingBuffer.claim` 取有限边界，与 `LogRepository.drain` 既有做法一致（[Java §5.2](../ogbs/OGBS-Data-Java-25-Specification-1.0.zh-CN.md#52-一轮保存)） |
| 脏集合没有上限 | D-WRITE-04：加上限，写入方先等 `pendingChangeWait` 再被拒绝；绝不为腾空间丢弃已接纳的变更 |
| 缓存没有条目上限 | D-CACHE-03：按 Repository 加上限，只淘汰干净条目 |
| 文档完全没提 `rewriteBatchedStatements` | [Java §6.2](../ogbs/OGBS-Data-Java-25-Specification-1.0.zh-CN.md#62-批量吞吐与-jdbc-url) |

同样的洪水场景现在是一条测试 `DatabaseIntegrationTest.unthrottledProducersAreBoundedAndEveryAcceptedChangeIsStored`，
对着同一个本地 MySQL 运行，各项上限调低以便在几秒内结束。四个不限速生产者跑五秒，
`maxPendingChanges=5,000`、`maxCacheEntries=5,000`、`pendingChangeWait=200 毫秒`、`flushInterval=100 毫秒`：

| 读数 | 修复前 | 修复后 |
| --- | --- | --- |
| `pendingChanges()` 峰值 | 8,079,251 且持续增长 | 5,002（上限 5,000，超出的是四个写入方） |
| 缓存条目峰值 | 无上限 | 10,007（上限，加上不可淘汰的脏条目） |
| 完成的轮数 | 0 | 8 |
| 接纳 / 拒绝 | — | 50,007 / 84 |
| close 之后 MySQL 中的行数 | — | 50,007，与接纳数相等 |
| 结果 | 7 秒 OOM | 平稳 |

接纳速率约 10,000 行/秒，正是 §3 中不带参数的 URL 的数值：测试读取的环境变量里没有
`rewriteBatchedStatements`，而这正是 §3 要说的那个缺口。

### 5.1 吞吐

这台机器上一共跑过三轮，彼此并非处处一致，所以本节给出互相复现的那两轮，并说明第三轮在哪里分道扬镳。带连接池，
每格 200,000 条变更，压测随后在 MySQL 中清点它们是否到位：

| 配置 | 不带参数的 URL | `rewriteBatchedStatements=true` | 该参数值多少 |
| --- | --- | --- | --- |
| INSERT，batchSize 500 | 13,640 | 58,080 | ×4.26 |
| INSERT，batchSize 2000 | 14,503 | 103,318 | ×7.12 |
| UPDATE，batchSize 500 | 10,822 | 16,546 | ×1.53 |
| UPDATE，batchSize 2000 | 10,395 | 11,147 | ×1.07 |

同一条命令在同一台机器、同一个库上的第二轮，与上表每一格的差距都在 5% 以内（不带参数 13,541 / 14,691 /
10,746 / 10,213，带参数 60,913 / 103,435 / 16,642 / 11,189），对应 ×4.50、×7.04、×1.55 与 ×1.10。更早的第三轮
在不带参数的 URL 上明显更低——INSERT 为 11,331 与 9,717——因而算出 ×5.3 与 ×10.9。那一轮里不带参数的 INSERT 在
batchSize 2000 下反而比 500 慢，而另外两轮都是相反的，所以这里把它当作一次异常运行，而不是第三种意见。带参数的
速率是这项测量里稳定的一半；不带参数的那一半会漂，任何建立在它上面的倍数都会继承这份漂移。

所以该参数对 INSERT 在 batchSize 500 下约值 ×4.3~4.5、在 2000 下约值 ×7，对 UPDATE 约为 ×1.5 与 ×1.1。§3 的
单一 ×3.8 不成立，不是因为它偏得多，而是因为一个数字表达不了它：合并后的 `VALUES` 随批次增大，所以批次越大该
参数越值钱；而根本无法合并的 UPDATE 则反向移动。
[Java §6.2](../ogbs/OGBS-Data-Java-25-Specification-1.0.zh-CN.md#62-批量吞吐与-jdbc-url) 记的是区间，而不是
任何一轮的末几位数字。

有一个数字现在由两套互相独立的压测确认，而不是同一套跑两遍：带参数、batchSize 500 的 UPDATE，这里是 16,546 与
16,642，§3 是 16,700，而 §3 的压测与这一套没有共用任何代码。这正是真实游戏会碰到的数字——有玩家之后 UPDATE 就是
热路径——也是最值得按它做容量规划的那个上限。

连接池的价值低于本节早先一稿的说法，而且吃亏的地方也不是它说的那里。用 `--pool=off`，即 `JdbcMysqlAccess`
每次操作都从普通 `MysqlDataSource` 取连接时，同样这八个配置分别得到不带参数 10,743 / 13,821 / 8,602 / 9,841、
带参数 49,461 / 56,044 / 8,594 / 9,334 行/秒，也就是 HikariCP 在不带参数时值 ×1.27、×1.05、×1.26、×1.06，带参数
时值 ×1.17、×1.84、×1.93、×1.19。也就是说，随配置不同从 5% 到 93% 不等，不是一律一半；而且规律也不是"批次越
小"：握手最吃亏的地方是批次自身的工作便宜的时候，batchSize 500 的 UPDATE 如此，被驱动合并成一条语句的 2000 行
INSERT 同样如此。§3 那个手写复用器的 +28% 落在这个区间里。连接池值得有，但不是瓶颈。

把同样这几格读成开关的倍率而不是连接池的倍率，会看出单看速率看不出的事。不带池时，这个开关对 INSERT 在
batchSize 500 上约值 ×4.6、在 2000 上约值 ×4.0，对 UPDATE 则是 ×1.00 与 ×0.95；第二轮运行与之一致（×4.51、
×4.98、×0.99、×0.88）。也就是说，正是连接池让这个开关对状态写入有价值可谈，而 2000 上那个 ×7 是带池的数字，
不是开关本身的性质。

### 5.2 生产速率

`batchSize 2000`、`maxPendingChanges 50,000`、`pendingChangeWait 200 毫秒`、四个生产者、带改写参数的 URL，
每个速率 20 秒。在 `flushInterval 1 秒`（§2 为洪水场景说明的那个条件）下：

| 生产速率 | pendingChanges（稳态 / 峰值） | 轮数 | 堆峰值 | 接纳 | 接纳/秒 | 拒绝 |
| --- | --- | --- | --- | --- | --- | --- |
| 30,000/s | 14,998 / 29,967 | 19 | 230 MB | 598,005 | 29,900 | 0 |
| 60,000/s | 29,677 / 50,000 | 19 | 108 MB | 1,000,004 | 50,000 | 0 |
| 不限速 | 50,001 / 50,003 | 19 | 118 MB | 1,000,028 | 50,001 | 320 |

在 `flushInterval 100 毫秒`（§2 自己那组稳态数字所在的区间）下：

| 生产速率 | pendingChanges（稳态 / 峰值） | 轮数 | 堆峰值 | 接纳 | 接纳/秒 | 拒绝 |
| --- | --- | --- | --- | --- | --- | --- |
| 30,000/s | 1,524 / 3,060 | 198 | 169 MB | 598,046 | 29,902 | 0 |
| 60,000/s | 3,024 / 7,968 | 197 | 189 MB | 1,194,236 | 59,711 | 0 |
| 不限速 | 50,001 / 50,003 | 43 | 217 MB | 2,250,065 | 112,503 | 340 |

这两张表说明四件 §2 无法说明的事：

1. **决定等待量的是 flushInterval，不是数据库。** 在排空速率以下，脏集合在"空"与"一个 flushInterval
   的产量"之间循环：30,000/s 下，100 毫秒间隔的峰值是 3,060、中位数是 1,524，1 秒间隔则是 29,967 与 14,998。
   这并不能解释 §2 的 400~1,500——本节早先一稿曾这样断言：那次运行 20 秒跑了 19 轮，间隔就是 1 秒，而该速率在
   1 秒间隔下会留下约 15,000 条等待。它的采样读到的是谷底（§2）。
2. **maxPendingChanges 与 flushInterval 共同为接纳速率设上限。** 一轮 pass 最多认领上限那么多，然后把间隔余下
   的时间等完，所以只要一轮 pass 还能装进一个间隔，上限就是「上限 ÷ 间隔」：在 50,000 与 1 秒之下，无论生产者
   推得多快，接纳速率都不会超过 50,000/s——这就是 60,000/s 与不限速两行都停在那里的原因，也是同样不限速的生产者
   在间隔改为 100 毫秒后能达到 112,503/s 的原因。想要更高的上限，部署时就提高上限或缩短间隔；这两行里数据库都
   不是瓶颈。
3. **背压先于拒绝出现。** 在 50,000/s 的上限之下跑 60,000/s，所有写入都被接纳、没有一条被拒绝：写入方在
   `admit` 里等待，而空间在 `pendingChangeWait` 之内就出现了。拒绝（320 与 340）只出现在完全不限速的生产者那里。
4. **上限守住了，已接纳的东西一条都没丢。** pendingChanges 峰值从未超过 50,003——上限加上已经进到里面的写入方——
   而 §2 是 8,079,251；堆峰值在 108 到 230 MB 之间，而 §2 是 2,045 MB 随后 OOM；`close` 之后表中的行数恰好等于
   被接纳的变更数，最多的一次是 2,250,065 条。做不到时压测会让该次运行失败。

§2 那次堆耗尽本身已经无法复现：D-WRITE-04 已经在代码里，脏集合会停在上限。唯一的回头路是把 `--max-pending`
往无上限的方向调大。

两次运行都未测：远程数据库、混合写入构成（而非单一操作）、带索引或宽表、MongoDB、真实故障期间（而非过载期间）
的行为，以及日志路径的任何方面——它有自己的队列与上限。
