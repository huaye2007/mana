## 1. Router Java review resolution and remaining limits

The Handler mutation, readiness and cleanup hooks have been removed from RPC. Ordinary Handler assembly, component-owned protocol maintenance and explicit application closure replace them. The reproduced callback lock cycle, multi-Slot Router restart, missing-register-ACK recovery, exact removed-incarnation resurrection and late post-close state mutation have code changes and permanent regression coverage. Service FIFO admission is now bounded; node-binding removal uses an owner index rather than scanning every binding.

RPC's deferred finite pending admission remains unimplemented. The forwarding monitor still covers encoding/sending and snapshot/conflict scans; resolveKey can scan Router buckets repeatedly. Production memory/throughput and sustained partition/overflow recovery are unverified. Removal fences are finite and not persisted across Router epochs; discovery replay and capacity planning are required. Further indexing, streaming snapshot generation or configured budgets need measured requirements; no new general-purpose extension framework is introduced.

The same-date follow-up findings now have implementation fixes and permanent regressions in [RouterRecoveryTest](../../game-router/src/test/java/cn/managame/router/node/RouterRecoveryTest.java). Inbound DATA uses the same readiness gate as outbound forwarding, preserving committed queries during repair while rejecting business delivery. A nontransient VERIFY failure stops registration recovery, exposes its error and preserves desired bindings for explicit retry; transport reconnection does not revive the stopped selection. The tests cover Notify/broadcast/Call/response rejection, ordinary RPC continuity, resynchronized delivery, malformed/nontransient verification ACKs, queued callback completion, explicit retry and transient/NOT_REGISTERED recovery. These changes enforce RT-SYNC-03 and RT-LIFE-02 rather than replacing their contracts. Temporary assessment probes are superseded by these maintained validation entry points.

Fix validation: `mvn -pl game-router -am test` passed with 37 Router tests, including ten new regression cases across the two review rounds. The two latest regressions failed against the old error-return and readiness implementations before their fixes. Root `mvn clean verify` passed Router and the other framework modules, but failed at game-demo test compilation because the existing DemoRpcBootstrapTest imports the absent GameRpcConfig. The same stale import and absent source were confirmed in HEAD before these changes. RouterEchoExample.run was independently compiled/executed during the earlier review against clean-built classes and returned `hello game-router`. This does not establish a successful full-root verification; the unrelated demo bootstrap compilation remains unresolved.

Capacity also needs a recovery-latency budget. At the default bucket limits, a snapshot requires 391 Node chunks, 3,907 binding chunks and HELLO/BEGIN/END: 4,301 acknowledged controls with one in flight per Peer. Ideal serialized ACK latency alone is therefore approximately `4,301 × RTT` (about 43 seconds at 10 ms RTT), before encoding, queueing and concurrent changes. Service restoration sends one acknowledged bind per desired key, so its corresponding term is `keyCount × RTT`. These are protocol-derived estimates, not measured throughput or recovery guarantees. Measure snapshot completion, restoration time, monitor hold time and pending memory before raising capacity or changing the confirmed ordering contract.

#### Architecture and responsibility assessment

The component ownership split remains consistent: RPC owns transport and call completion; Router owns registration, authoritative buckets, synchronization and forwarding; discovery owns instance retirement; application/Runtime own business placement and execution. The remaining architectural gaps below do not justify reversing dependencies, a second RpcNode, a Router business pending map or a general extension framework.

- **Incarnation and discovery integration needs an operational contract.** RouterEngine.locate selects the greatest unsigned nodeEpoch, but ServiceRouting.register requires only a distinct nonzero epoch, not an increasing value. A temporary real TCP probe under ignored `game-router/target/router-architecture-review` registered/bound replacement Node 1/epoch 1 at B after Node 1/epoch 10 lost transport at A. Both operations succeeded; after Router synchronization, epoch 10 remained visible and a routed call returned PEER_NOT_FOUND. Exact `A.removeNode(1,10)` made epoch 1 visible and a fresh call succeeded. This is an existing deterministic selection boundary, not a violation or evidence of automatic failover. A deployment must supply exact retirement/replay and explicitly decide whether epoch allocation is ordered; numeric conflict selection alone cannot supply discovery authority. A new epoch at the same Router also cannot replace its retained conflicting local registration before retirement/detach. Router membership removal uses only an ID (`unregisterRouter(int)`), so discovery integration must fence delayed Router-offline events against its own current incarnation before removing membership. These integration mechanisms are not supplied by RouterEchoExample.
- **Managed Spring RPC and routed Runtime assembly are not composed.** [RpcConfiguration](../../game-spring/src/main/java/cn/managame/spring/rpc/RpcConfiguration.java) runs GameRpcConfigurer first; [GameRpc](../../game-spring/src/main/java/cn/managame/spring/rpc/GameRpc.java) then overwrites the Builder Handler with its private direct-RPC Handler. That configurer cannot install GameRouter/ServiceRouting around the managed application Handler, and RpcNode has no post-build Handler mutation. [RpcHandlerContext](../../game-runtime/src/main/java/cn/managame/runtime/context/RpcHandlerContext.java) also lacks source attachment epoch; GameRpc.reply uses a native direct reply, whereas ServiceRouting.reply needs exact routed source identity. An optional game-spring/application adapter needs pre-build composition, routed reply identity, protocol decoding, callback Route capture/drain and lifecycle ordering. Reuse existing RPC/Runtime mechanisms; do not copy correlation into Router or create another Node. This adapter is unimplemented, not implied by ordinary Handler composition or managed direct RPC tests.
- **Routing placement is not business execution fencing.** RT-BIND-03 already assigns exclusive placement to the application. Neither a successful bind, deterministic winner selection nor the process-local Runtime executor proves that an old owner has stopped changing player/room state. Migration integration needs an application-owned ownership generation checked by the execution/storage owner, and an explicit drain/state-transfer sequence where required. Source nodeEpoch only fences a Node attachment; it is not a per-binding business ownership generation. This capability is outside Router and no end-to-end migration/fencing test is supplied by the current routing example.
- **Control/data coupling and full replication bound the deployment shape.** One Router Slot carries synchronization and business envelopes, and the same forwarding monitor performs state and forwarding work. A synchronization reset blocks business forwarding through readiness even if transport and the committed bucket remain available. Independent DATA_ERROR admission removes ACK-queue dependency but does not establish network bandwidth isolation. With R Routers, full mesh has R×(R−1)/2 pair connections, up to R−1 control sends per local change, and a copy of global authoritative state at each Router. Small-fleet budgets should be measured before changing this topology. Bounded synchronization pipelining and shorter monitor scope are the first candidates; separate ordered control/data transport paths or sharded authority need a deliberate protocol/consistency design if measured scale requires them. None is implemented by this assessment.

This assessment adds no runtime behavior or new MUST requirements. The epoch boundary was checked by a temporary TCP probe; Spring/Runtime composition findings were verified from their current assembly and context/reply sources. Other architecture limits are contract-derived rather than production measurements.

#### Reconsidered recommendations and Java implementation sequence

These recommendations refine the preceding review; they remain pending implementation. No Java API, error mapping or Router Profile bytes are changed by documenting them. The language-independent identity/migration/control reasoning is in Router Specification section 7.

**Epoch necessity was checked, not assumed.** The temporary TCP architecture probe also restarted source Node 1: old epoch 10 and fresh epoch 1 both issued business requestId 2. A delayed reply for the old attachment was dropped; a reply for the fresh attachment completed its call successfully. RpcNode.requestIds is per-instance and starts at 1; pending completion and physical connection identity do not supply a routed attachment identity across restart. Preserve nodeEpoch/routerEpoch equality protection while IDs remain reusable. Numeric maximum is not evidence of freshness and should be removed from the recommended future identity resolver. Exact-pair resolution and ambiguous-ID rejection need dedicated maintained regressions and consistent conflict semantics before that behavior changes. Making Node IDs permanently unique is a possible alternative, but changes deployment allocation/exhaustion rules and cannot simply recreate the shared RPC Node on every routing selection without affecting ordinary RPC lifetimes.

**Implement migration in the application integration.** Use an application-owned per-key gate and operation/continuation tickets; transition its business phase on the existing Runtime Route. Asynchronous completion holds its ticket until protected work ends; blocked/rejected dispatch must release it. Freeze is local to the migrating object. GameRuntime.shutdown/awaitTermination covers an entire Runtime, is not a resumable per-key gate and must not be called/waited from that Route. Await per-key settlement through callbacks in a management workflow. Tag continuations and queued persistence with the captured ownership version. A frozen A can finish its already admitted work before transfer, but cannot admit new work or regain ownership on a delayed callback.

The normal migration order is durable prepare, confirmed old unbind, conditional owner commit, then B activation/bind. Check ServiceRouting.bindings after successful unbind: its desired key must be absent, otherwise automatic restoration could reclaim it. Timeout alone does not confirm unbind; reconcile through the existing service control state before committing transfer. Keep migrationId/checkpoint/version in the authoritative record so unknown transaction outcomes can be read and resumed idempotently. B remains prepared until commit, and failed post-commit publication leaves A frozen while B retries under the same migration ID. Retained remote claims can temporarily reject B's bind; this is an availability gap, not permission to override RT-BIND-01. Important caller retries reuse an application operationId with an atomically recorded result.

The ownership predicate and protected state change must share a transaction/conditional write, using native application database access initially. [Data Specification](../ogbs/OGBS-Data-1.0.md) makes Repository.update asynchronous admission, not a per-object durable checkpoint or fenced transaction; Runtime drain also proves neither persistence nor external delivery. A per-object persistence acknowledgement and token-checked write path are implementation prerequisites, not current game-data capabilities. A queued old-version write cannot borrow the new owner's token at flush time. Do not use GameData.close to flush one migrating player. Start with graceful migration and exact whole-incarnation discovery retirement. Forced per-key retirement while leaving the Node alive additionally needs binding ownership-version/authority integration; a new management removeBinding(key,expectedNodeEpoch) method alone would miss an A→B→A ABA case.

**Refactor synchronization without expanding public roles.** Candidate package-private helpers for authoritative/indexed state, Peer synchronization and forwarding keep GameRouter/ServiceRouting public boundaries unchanged. Under a short state monitor capture a routing decision or a compact consistent snapshot view and its revision; encode/notify/call outside the state monitor, with private buffers/retained references released on every outcome. Snapshot capture itself remains O(entries) if copying arrays; bound and measure that critical section rather than claiming streaming eliminates it. Consider versioned/structurally shared views only if capture exceeds measured budgets. Effective indexes preserve all candidate provenance and deterministic current rules until their explicit contract change.

Each Peer sender serializes write admission and has one scheduled-drain marker, a bounded ACK window and both per-Peer/process byte accounting. HELLO/BEGIN acknowledgements are phase barriers; pipeline ordered Node/binding chunks and later consecutive deltas, with END after preceding snapshot success. A failed window fences all callbacks using its local generation/Peer identity before resetting. Materialize chunks lazily; count captured views, staging, logical deltas, encoded and in-flight buffers in budgets. Budget rejection before local mutation is different from existing remote overflow after local acceptance: new admission limits require explicit two-layer contract updates. Rate-limit drain work and use per-Peer recovery backoff so ACK callbacks do not monopolize an EventLoop or continuously rebuild snapshots. Window size derives from measured bandwidth/RTT and global limits, not a promised throughput default.

Strict control/data transport separation is a subsequent RPC integration change. RpcPeer.startSlot and RpcNode.send use routeKey as a starting slot and then try alternatives, so a routeKey convention cannot isolate traffic. RPC would need strict Slot send/admission and Slot availability/binding-generation evidence; it still owns connections, recovery, body consumption and pending completion. Router's proposed two-Slot role mapping, stream-attempt fencing and readiness on channel loss must be documented in a coordinated Router Profile revision before changing current one-Slot validation. This creates no second Node and does not permit stale-bucket forwarding. Keep the full mesh initially; configurable membership, aggregate bytes and simultaneous-snapshot limits make its deployment boundary explicit.

Required future validation includes delayed responses/removals after ID reuse; callbacks/writes after A is frozen or ownership transferred; unknown commit/unbind outcomes; desired-binding restoration after lost ACK; B bind blocked by stale authority; ticket rejection/release and operation deduplication; window ACK failures/reordering, old callbacks and invisible staging; bounded bytes under sustained load; shutdown/reference ownership; and strict Slot failure without cross-role fallback. None of those proposed features is certified by the existing 37 Router tests or the temporary probes.

#### Continued capacity and failure-path assessment

Recommended implementation sequence for the remaining synchronization and aggregate-capacity risks is an evaluation plan, not an active requirement or implemented feature:

1. Measure per-Peer control arrival/drain rates, queued and in-flight bytes, ACK latency, snapshot/restoration duration, resets by cause, monitor hold time and aggregate committed/staging/index memory. Compare sustained change rate with measured drain capacity, including recovery traffic.
2. Evaluate a bounded in-flight state-control window on the existing single Slot. Preserve ordered application and consecutive revisions; count and byte bounds must apply to both queued and in-flight work. END acknowledgement alone cannot enable readiness until all preceding snapshot controls have succeeded. Any failed or superseded window must fence all its late callbacks before fresh synchronization. The current one-in-flight rule in this Java specification and Wire Profile would need coordinated changes and concurrency/failure regressions; choose a window from measurements, not an unverified fixed default. Generate snapshot chunks lazily from a captured immutable view, with reserved delta capacity and unchanged snapshot-before-delta order. Batched deltas or service binding restoration are a later option requiring explicit wire operations, version/compatibility review and tests; skipping revision-bearing mutations is not safe coalescing. If arrival still exceeds drain capacity, application rate budgets or an explicit admission policy are necessary; a larger FIFO alone only delays overflow.
3. Reduce forwarding monitor scope by capturing immutable routing decisions/identities and necessary retained payload references under the lock, then encoding/sending outside it with release on every outcome. Preserve close/admission boundaries, control enqueue order and snapshot consistency; never iterate live mutable tables outside the lock. Evaluate an effective node-location index and winning-binding index only with provenance for all candidate buckets, so removing a winner reveals the correct competing claim under existing deterministic conflict rules. The existing owner-to-key removal index already solves a different scan.
4. Define process-wide and per-Peer byte budgets covering committed state, staging, queued/in-flight controls and fan-out, plus Router membership and concurrent recovery limits. Making these configurable and rejecting previously accepted work changes public defaults/admission behavior, so both specification layers and boundary tests need a deliberate design update. Discovery removal fences require an authoritative incarnation retirement/checkpoint rule or operational rollover with discovery replay; timeout/LRU eviction cannot safely solve their lifetime cap.

The subsequent local assessment contains resolved deviations and remaining capacity risks below. Temporary TCP probes under ignored `game-router/target/router-followup-review` supplied initial local evidence, not production capacity tests. Error-return blocking and Slot reconfiguration deviations now have code fixes and maintained regressions; the other items remain unimplemented.

- **Reconfigured Router Peers can retain invalid READY state (resolved).** The implementation previously reported READY after reconfiguration to two Slots. Readiness, unicast and broadcast now check the current Slot count; maintenance invalidates unsuitable synchronization while retaining committed queries, and restoring one Slot exchanges fresh snapshots. Section 2 and the permanent `routerSlotReconfigurationInvalidatesReadinessAndRequiresNewSnapshot` regression define and validate this boundary.
- **Business Call pending admission is unbounded (confirmed existing RPC capability gap).** A real local Router delivered 10,000 Calls to a service that consumed requests without replying. The source used 60-second call timeouts; all 10,000 calls remained in its RPC Peer pending map with no admission failures. The bounded service-control FIFO does not bound these business calls, and writable TCP does not imply response capacity. This confirms the missing admission mechanism rather than an out-of-memory threshold or supported throughput. Node-level Call admission belongs to RPC's deferred R-SEND-04; Router must reuse its completion semantics rather than add another business pending map. See [RPC Java specification](../ogbs/OGBS-RPC-Java-25-Specification-1.0.md). Timeout removes pending state and reports TIMEOUT; late responses do not complete again. This is not permanent leakage: the risk is concurrent accumulation before timeout, approximately arrival rate multiplied by average waiting time.
- **Routed errors wait behind synchronization ACKs (resolved).** The initial probe withheld a VERIFY ACK, disconnected the destination service and observed PEER_NOT_FOUND DATA_ERROR queued behind synchronization while a 200 ms Call timed out. Error returns now independently attempt Notify admission. The Wire Profile records this representation and acceptance of the older Call form. The permanent `routedErrorDoesNotWaitForSynchronizationAcknowledgement` regression covers the fix; it does not guarantee delivery over an unavailable return path.
- **Sustained change can outrun serialized synchronization (protocol-derived capacity risk).** With one acknowledged control in flight, ideal drain rate is at most roughly `1 / RTT` controls per second. Local registrations, binds and unbinds can arrive from many services; they succeed without waiting for remote drain. If their aggregate arrival rate exceeds the drain rate, the 8,192-control queue eventually overflows, resets the stream and starts another full snapshot. At the maximum snapshot size, approximately 3,892 queued slots remain for subsequent changes if no ACK has drained during capture. Continued overload can repeatedly destroy snapshot progress. Existing convergence is conditioned on source state becoming quiet; no sustained-load recovery budget has been verified. Service restoration's one-bind-per-key flow likewise keeps outbound business routing unavailable until the desired set has been restored.
- **Per-bucket limits do not establish a process resource budget (structural, unmeasured production risk).** Configured Router membership has no aggregate cap; each Peer can retain a committed bucket, stage another bucket and own an encoded control queue. Tables also maintain an owner-to-key index. Memory therefore grows with source buckets, concurrent recovery and fan-out, not just the local one-million-binding limit. Snapshot encoding, conflict scans and business encoding/fan-out run under the same monitor; blocking there can delay other RPC connections on shared EventLoops. `resolveKey` can perform quadratic Router-bucket work when many buckets claim the same key; service-wide inspection scans all registrations and repeatedly locates owners. Measure bytes, monitor hold times and tail latency before selecting indices or budgets. The separate 100,000-pair removal fence is a lifetime limit, so discovery-event churn also needs an operational budget; exhausting it rejects a new removal before clearing its live route, as section 2 explicitly specifies.

<a id="rpc-integration"></a>

## 2. RPC/Router integration review

The reproduced topology-listener/service-monitor lock cycle was removed by deleting the RPC hooks and moving service sending/application completion outside routing state protection. Router is supplied as an ordinary Handler at Node construction. Protocol-owned registration verification handles remote Router replacement even when multiple Slots keep transport continuously available; application-owned routing close fences late state mutation before RPC resource closure. See [Router review resolution](#router-java-review) and its permanent regression tests.

Only read-only Peer availability/count queries were added to the RPC Node; handshake, send, pending, timeout and closure mechanisms retain their existing implementation. R-SEND-04 finite pending admission remains unimplemented. Router's separate service control FIFO is now bounded, but that does not bound ordinary/business RPC calls to a slow reachable Peer. Production throughput, memory and overload limits remain unverified; prioritize actual admission requirements without introducing routing policy into RPC.

## 3. Proposals: identity, migration and control/data coupling (moved from the Router Specification)

The following is a reasoned recommendation, not an implemented behavior or a replacement for the confirmed clauses above. In particular, RT-BIND-03 still uses numeric epoch conflict selection and forwarding still requires bidirectional readiness. A later implementation must update those clauses, Java bindings, interoperability rules, examples and failure tests together.

**Identity.** Retain incarnation identity while nodeId may be reused. nodeEpoch identifies a service attachment: reconnecting the same attachment keeps it; restarting/reselecting creates a distinct token. routerEpoch identifies a Router lifetime; revision orders changes within that lifetime. These tokens need equality checks, not chronological comparison. Removing them would require never reusing Node identities, or carrying equivalent registration/connection-incarnation identity through forwarding, replies and discovery events. Connection identity alone cannot identify a delayed reply crossing intermediary Routers, and a new RPC Node starts its call-ID sequence again. Moving attachment identity to another field would not remove the requirement.

The recommended change is to remove numeric epoch-based winner selection, not blindly delete the token. Resolve explicitly addressed `(nodeId,nodeEpoch)` replies/deliveries against the exact attachment; when nodeId-only or binding lookup has incompatible incarnations without an authoritative retirement decision, diagnose the conflict and reject routing as unavailable. Retain candidates until exact discovery cleanup; do not guess which instance is newer. This changes conflict behavior and needs a coordinated compatibility decision. Node incarnation is also different from the per-player/room ownership version used below.

**Normal business migration.** Keep one ownership record per business key in the application's authoritative transactional store: owner attachment, ownership version, migration ID, phase and durable checkpoint. The recommended sequence is: conditionally claim migration intent while A remains owner; freeze admission for that key at A; drain accepted work and all continuations; confirm a durable checkpoint and prepare B without execution; confirm A's unbind so the service's desired set also forgets the key; conditionally commit ownership to B with a new version; activate/publish B's binding. Ownership commit is the transition's authoritative point; route publication is eventually consistent and may lag. A stops execution after transfer even while callers hold stale routes. B's bind may encounter A's retained remote claim and must wait/retry control publication within the migration policy, not override it. Migration completes locally only after B is active and its bind succeeds, without claiming cluster-wide visibility.

Per-key freezing/draining belongs to the application's business lifecycle, using the existing Runtime Route for serial state changes. Track admitted operations and their asynchronous continuations until they settle; a queue marker or a returned Handler is not sufficient. Do not call whole-Runtime shutdown to migrate one player. Route work must not wait for its own drain. An unbind timeout is an uncertain result, not permission to commit takeover; settle it through existing control recovery/reconciliation first. Before ownership commit, abort can restore A only after confirming that A still owns that version and reconciling its binding. After commit, retry activation/publication under the same migration ID; never revive A because a reply or bind ACK was lost.

**Crash takeover and effects.** An authoritative transaction changes owner/version, and every protected state write checks that owner/version in the same atomic operation as its effects. This prevents a paused old instance from committing after takeover, even if it misses discovery notifications. Checking ownership once before a later unconditional write is insufficient. Use one transactional store for the ownership guard and protected state where possible; an external coordination record alone does not fence a different database. Queued writes retain the version that authorized them, not the version current when a save worker eventually runs. Important external effects need a fenced recipient or a transactional outbox/idempotency contract. Unpersisted memory is not recovered by fencing.

The first implementation should support graceful per-key migration and discovery-confirmed whole-incarnation retirement. If an unreachable A's binding cannot be authoritatively cleared, B waits/fails migration rather than forcibly creating competing bindings. Safe forced transfer of one key while retaining A's other keys requires additional per-binding retirement/ownership-version integration; owner Node/epoch alone has an ABA risk if the key later returns to the same attachment. That extension is not supplied by current bind/unbind/removeNode APIs. Calls requiring explicit recovery use business operation IDs and transactionally stored results; Router does not automatically retry business messages, and Notify retains its existing loss boundary.

**Control/data solution.** Keep the small-fleet full mesh and current readiness safety boundary for the first stage. Separate authoritative state, per-Peer synchronization and forwarding internally; shorten state critical sections and perform encoding/sending outside them using captured identities. Send synchronization with a count-and-byte-bounded window, generate chunks from a consistent captured snapshot on demand, reserve delta budget and rate-limit control injection. Identity/BEGIN stages remain acknowledged barriers; END/readiness waits for every preceding snapshot control to succeed. Failed generations fence late callbacks and repair only their routing stream. Budget aggregate committed/staging/index memory, membership and concurrent snapshots as well as each Peer queue. Sustained arrival above drain capacity requires explicit source admission/rate limits or recovery backoff; no finite queue guarantees convergence under unlimited load.

This stage reduces coupling but does not physically isolate bandwidth on the shared Slot or allow forwarding through unready state. If physical isolation is required, the proposed next stage is two role-defined Slots on the same RPC Node/Peer: ordered state controls and business/error traffic. RPC must supply strict Slot admission without fallback across roles; current routeKey affinity can fall back and is insufficient. Control-channel replacement also needs synchronization-attempt fencing. Slot failure/readiness, queue ownership and protocol compatibility must be specified before removing the current one-Slot constraint. Authority sharding is a later topology change if measured global replication budgets require it, not an incidental implementation refactor.
