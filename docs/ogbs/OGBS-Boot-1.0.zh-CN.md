# OGBS 服务器组合规范 1.0

[English](OGBS-Boot-1.0.md) | **[简体中文](OGBS-Boot-1.0.zh-CN.md)**

把能力组件拼装成一个可运行服务器的那一层，其语言无关职责。本仓库在 game-boot 中实现；配套文档：[Java 开发规范](OGBS-Boot-Java-25-Specification-1.0.zh-CN.md)。被拼装组件自身的契约——[Runtime](OGBS-Runtime-1.0.zh-CN.md)、[RPC](OGBS-RPC-1.0.zh-CN.md)、[Data](OGBS-Data-1.0.zh-CN.md)、[Network](OGBS-Network-1.0.zh-CN.md)、[Core](OGBS-Core-1.0.zh-CN.md)——仍然是权威，本文件不削弱其中任何一条。

## 1. 这一层是什么

一次部署需要的东西比能力组件更多。必须有人决定：一个入站 RPC 帧要变成一次 Route 调用，就绪探针要在业务分发之前被回答，关闭的各个阶段加起来要等于某个人真正选定的预算。这些都不属于任何一个能力组件：Runtime 不该了解 RPC 线格式，RPC 不该了解 Route，Network 不该了解读数契约。同样，它们也都不属于容器：无论应用是手工接线、用依赖注入还是读配置文件，要做的是同一件事。

所以这一层只为这些接缝而存在，别无其他。它是唯一被允许同时依赖多个能力组件的层，而这恰恰就是适配代码放在这里、各组件彼此无感知的原因。

**B-COMPOSE-01**：此处定义的每一处拼装都**必须**在没有容器的情况下可用。每一处都是一个普通对象，应用用自己已有的输入构造它、持有它、关闭它。容器集成**可以**决定一个列表的顺序、读取配置、持有生命周期回调，但**不得**成为某处拼装存在的唯一位置，也**不得**在其之上叠加自己的可观察行为。判据是具体的：一个不使用任何容器的应用**必须**能拼装出同一个服务器，并且**必须**观察到相同的顺序、失败与所有权。

**B-COMPOSE-02**：组合**不得**为被拼装的组件新增能力。它不引入第二条执行队列，不引入调度器、服务发现、自动重试、认证或可靠投递。准入、顺序、排空、错误策略与资源所有权仍由被拼装组件自身定义；本规范只说明这些契约在何处相接，以及接缝两侧各自拥有什么。

**B-COMPOSE-03**：一处拼装**必须**拥有自身契约的全部。当某个钩子、阶段或清理步骤属于这处拼装所承诺的内容时，由这处拼装自己执行，而不是把其中一部分留给调用方重复一遍。调用方遗漏了一个从未被告知的步骤，这是接缝的缺陷而不是调用方的缺陷——并且被切开的契约也正是第二个集成会与第一个产生偏差的原因。

例如，§2 的 RPC 适配器自己调用全部四个 configurer 钩子。此前的安排是由容器调用第一个钩子、适配器调用其余三个；这正是 B-COMPOSE-03 所禁止的形状，因为一个不使用容器的调用方根本无从得知第一个钩子的存在。

<a id="2-rpc-adapter"></a>

## 2. RPC 到 Runtime 的适配器

**B-RPC-01**：显式拼装出来的 RPC 适配器拥有业务编解码、协议查找与 Runtime 分发。它在普通 Handler 准入之前，把借用的传输体解码为独立对象，并带着收到的 Route Key、业务身份、Metadata 与逻辑来源进行分发。Domain 由 Handler 声明选择——传输不携带它，适配器也**不得**推断——并且适配器**不得**为经由 RPC 到达的工作伪造一个客户端 Connection。

**B-RPC-02**：Call 的响应类型来自请求绑定。一次 Call 要求调用方当前处于 Runtime Route 上；它注册的成功与失败续体回到那条确切的来源 Route，并参与排空。同步拒绝**不得**遗留被占用的续体，并且**必须**只报告一次失败：调用方从拒绝本身得知，而不是再通过续体得知一遍。对象回复保留 RPC 来源 Slot 偏好与替换连接回退；Notify 不可被回复。业务返回值不会自动回复，业务准入之后抛出的错误仍遵循普通的 Runtime 错误策略——希望调用方看到错误的应用显式回复一个错误。

**B-RPC-03**：适配器拥有它所构建的 Node。组合钩子按一个声明好的顺序运行：调整传输设置，然后包裹适配器自己的 handler，然后在 build 之后、start 之前 attach。detach 在 Node 关闭之前按逆序运行。attach 失败**必须**按逆序 detach 已经 attach 的部分，并关闭这个尚未启动的 Node，使得半 attach 状态的 Node 绝不会被交还出去。关闭是幂等的。适配器会替换钩子安装的任何 handler，因为向 Runtime 分发正是适配器存在的意义；需要看到流量的钩子应改为包裹 handler。

例如，一个服务角色路由层包裹适配器的 handler，把它作为自己的直连 handler，在 attach 中针对已构建的 Node 启动，在 detach 中关闭。被路由的请求于是到达路由层而不是 Runtime 分发，它们随后如何进入 Runtime 属于应用代码。

## 3. 关闭预算

**B-CLOSE-01**：关闭的各阶段**必须**一起编列预算，而不是分开配置。关闭按顺序运行它们——退出轮转、排空已准入工作、刷写最后的变更——因此部署需要覆盖的是总和，而分别配置各阶段的方案会产生一个没有人选过的总数。总预算因此是被配置的那个值，排空时间由它推导得出，于是总和不会漂移。两条推论是规范性的。刷写保留一个有保证的切片，而不是排空剩下多少用多少，因为丢掉最后的写入比截短排空更糟，并且排空是只等待的阶段、刷写才是真正写库的阶段。另外，默认总预算**必须**取在普通编排器杀进程前所给宽限期之下，因为比宽限期更大的预算不是更长的关闭而是丢失的关闭：杀进程落在排空中间，刷写永远不会运行。使排空无剩余时间的切分**必须**在启动时失败。

**B-CLOSE-02**：第一个阶段在工作仍被准入时就报告不就绪。就绪与准入**不得**在同一瞬间改变：负载均衡器只在下一次探测时才得知不就绪，因此一个在开始报告的同一刻就停止接受的实例，会拒绝这期间发来的一切。所以在一个可配置的前导时间里，本规范报告 B-OBS-02 的轮转条件为失败，同时继续准入、照常服务到达的请求；落在这个窗口内的 Timer 或 Cron 仍会触发。前导时间没有默认值，因为只有部署知道自己的探测间隔；位于负载均衡器之后的部署**应当**把它设为至少一个探测间隔，没有就绪探针的部署**应当**保持为零。前导结束后准入关闭，这同时停止后续调度：准入一旦关闭，被触发的 Timer 其提交会被拒绝并丢弃，所以让调度器在排空期间继续运转只会丢弃而不是执行；跨重启存活的持久化定时器仍是一项独立且尚未实现的能力。

无论由谁触发这个序列——容器的关闭事件、信号处理器，还是应用自己的 `main`——观察到的阶段与顺序都相同。触发是集成的工作；预算和阶段不是。

<a id="4-observability-composition"></a>

## 4. 可观测性组合

Core 定义什么是一条读数，各组件定义自己有哪些读数；组合是把它们收集起来、并回答"这个实例该不该接收流量"的地方。

**B-OBS-01**：组合为每个已拼装且存在的组件发布一个读数源，各自位于固定前缀之下——`runtime`、`data`、`rpc`、`network`——这样一块仪表盘可以读取本框架的任意部署。未被拼装的组件什么也不发布，而不是发布零，因为"组件缺失"和"组件空闲"是两回事。应用自己在拼装之外创建的组件，由它自己负责发布。

**B-OBS-02**：就绪是与读数不同的问题，**不得**由读数经阈值推导而来。它是一组具名条件，每条要么成立要么不成立；只有全部成立结果才是就绪，不就绪时**必须**指名未成立的条件。组合为每个"可能停止接受工作"的已拼装组件贡献一条条件——准入开放、变更被接受——此外不再贡献：一个实例是否就绪服务玩家，还取决于框架并不拥有的策略，例如是否已接入 Router、世界是否已加载，这些由应用作为自己的条件贡献。

**B-OBS-03**：就绪与读数**必须**在实例陷入麻烦时仍可被回答。因此它们在业务分发之前、在任何业务执行队列之外被服务，并且一条条件**必须**用自己已经持有的状态作答，不得阻塞、不得分发、不得去拿一个饱和实例可能正持有的锁。无法作答的条件计为不就绪。这正是要点所在：一个排在它所报告的工作后面的端点，在唯一重要的那一刻什么也说不出来。

**B-OBS-04**：关闭是可见的。排空先关闭准入再停止工作，所以实例还在完成已接受工作时，就绪就已经报告不就绪——这正是负载均衡器能在进程消失之前停止发送的原因。读数在全过程中持续作答，包括准入关闭之后。

**B-OBS-05**：暴露格式不在此规定。组合**可以**用自选格式提供读数；需要某种特定格式的应用实现 Core 的 sink 并映射名字。通过 HTTP 提供时，路径是绝对的，并且独立于任何已配置的业务路径前缀，这样探针不需要知道前缀，前缀也既不会暴露也不会遮蔽它们。只服务读取方法；其他方法都是普通业务流量。

<a id="5-business-path-prefix"></a>

## 5. 业务路径前缀

**B-HTTP-01**：应用**可以**把全部业务 HTTP 端点放在一个公共前缀之下，而端点声明无需知道它。匹配使用完整的原始路径段，保留查询串，绝不静默解码或重定向到另一个路径；前缀之外的请求返回 404 且不执行业务。端点观察到的是相对于前缀的目标。映射**不得**修改传输所拥有的那个请求：需要不同目标的实现产生自己的视图并释放它（包括分发失败时），原请求保持不变，交由传输释放。非法前缀是配置处的配置错误，而不是请求期的失败。

例如，前缀 `/game` 把 `/game/status?id=7` 映射到已注册的 `/status` 端点，查询串仍是 `id=7`；`/games/status` 与 `/game%2Fstatus` 不匹配，`/game` 和 `/game/` 都映射到 `/`。§4 的可观测性路径在应用此前缀之前匹配，因此无论前缀是什么，探针都在服务器根路径上够到它们。

## 6. 验证与限制

Java 验证入口：[BootRpcCompositionTest](../../game-boot/src/test/java/cn/managame/boot/rpc/BootRpcCompositionTest.java) 在没有容器的情况下拼装 §2 的适配器，覆盖入站 Notify 与 Call、出站 Call 在来源 Route 上完成、钩子顺序以及 attach 失败后的清理；[ObservabilityEndpointsTest](../../game-boot/src/test/java/cn/managame/boot/metrics/ObservabilityEndpointsTest.java) 覆盖 §4；[HttpContextPathTest](../../game-boot/src/test/java/cn/managame/boot/http/HttpContextPathTest.java) 覆盖 §5；[ShutdownBudgetTest](../../game-boot/src/test/java/cn/managame/boot/lifecycle/ShutdownBudgetTest.java) 覆盖 §3 的推导、默认值与应被拒绝的切分。

这些测试未验证：生产环境资源耗尽、卡死的存储驱动、跨进程关闭、部署安全、负载下的 RPC 容量，以及除 Java 规范所述朴素格式之外的任何暴露格式。B-CLOSE-02 的前导时间由拥有触发点的容器集成来验证，见 [MetricsAssemblyTest](../../game-spring/src/test/java/cn/managame/spring/metrics/MetricsAssemblyTest.java)。

## 7. 已确认的取舍

| 决定 | 原因 | 重新考虑的触发条件 |
| --- | --- | --- |
| 组合自成一层，而不是容器集成的一部分 | 只随某一个容器的接线一起交付的拼装，对其他所有应用都不可用，第二个集成只能重新实现而不是复用 | 某处拼装被证明需要只有容器才能提供的东西，那就说明它本来就不是组合 |
| 一处拼装拥有自己全部的钩子（B-COMPOSE-03） | 在拼装与调用方之间切开的契约，对未被告知的调用方不可见，并且会在不同集成之间产生偏差 | 仅凭此理由不再重新考虑；确实需要容器状态的钩子应改为属于集成 |
| 就绪是具名条件而非读数阈值 | 阈值回答的是"某个数字是否偏高"，而问题是"流量该不该来这里"，而且无法说出是哪条条件未成立 | 某个部署需要一条框架无法表达为"已持有的布尔值"的条件 |
| 关闭总预算被配置、排空时间被推导 | 分开配置各阶段会产生没有人选过的总数，并且杀进程会落在超时的那个阶段中间 | 编排器把宽限期暴露给进程，这将使总预算可以读取而不是配置 |
