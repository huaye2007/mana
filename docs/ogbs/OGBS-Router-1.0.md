# OGBS Router Specification 1.0

**[English](OGBS-Router-1.0.md)** | [简体中文](OGBS-Router-1.0.zh-CN.md)

Document type: language-independent Specification. Component: game-router. Companion: [Java 25 Development Specification](OGBS-Router-Java-25-Specification-1.0.md). Dependencies: [RPC](OGBS-RPC-1.0.md), [Core](OGBS-Core-1.0.md). Bytes: [Router Profile in RPC Wire Profile](../rpc-wire.md#router-profile-v5). Status: implemented Java reference; local TCP contract tests exist. Production capacity and cross-language interoperability are unverified.

Routers form a mesh and relay for the service Nodes attached to them. A service Node connects to **one** Router and announces itself there; each Router tells the other Routers which Nodes are attached to it. A message for an exact Node goes to the sender's Router, which either delivers it to a Node attached to itself or passes it once to the Router that Node is attached to. Resolving a business key such as a player to a Node still belongs to the sender. Open limits are in the [Java known limits](OGBS-Router-Java-25-Specification-1.0.md#7-known-limits).

## 1. Responsibility and composition

**RT-SCOPE-01** Router MUST build on RPC for sending, receiving, direct-Peer connections, Slots, call IDs, pending calls, timeouts and callbacks. A process has one RPC Node; installing routing MUST NOT create another Node or independent transport. An application may still use that same Node for ordinary direct RPC. Router owns relaying only; the application owns RPC startup, shutdown and Peer configuration, and connects to a Router with the same RPC Peer operation as to any other Node. Declaring which Routers a service or a Router uses MUST NOT create or remove RPC Peers: choosing which Router a service connects to, and reconnecting it elsewhere when that Router is gone, is the application's decision.

**RT-SCOPE-02** V1 provides exact Node addressing and service broadcast through a two-tier mesh: service Nodes attach to one Router, and Routers interconnect. Router does not resolve business keys, keep bindings or registrations, implement discovery or subscriptions, store or retry messages, hold player state or provide Runtime serial execution. The only thing Routers replicate to each other is which Node is attached where, which is bounded by the number of Nodes and never by business keys. A routed message crosses **one Router when its target is attached to the sender's Router and two otherwise**; it is never relayed through a third Router. RPC success or timeout never proves exactly-once business execution.

| Owner | Responsibility |
| --- | --- |
| RPC | Connections and Slots, message transport, call IDs, pending calls, timeouts and completion callbacks |
| Router | Delivering to a Node attached to itself, passing anything else once to the Router that Node is attached to, and telling the other Routers which Nodes are attached to itself |
| Sending service | Resolving a business key (player, room) to a Node ID |
| External discovery | Which service instances and Routers exist, and their addresses |
| Application | Component assembly, startup/shutdown, choosing each service's Router and reconnecting it elsewhere, and connecting the Router mesh |

Rationale: connecting every service to every Router cost `services × Routers` connections and made every Router hold an announcement for every Node anyway. Attaching a service to one Router costs `services + Router pairs` connections and moves the fan-out into the mesh, where it is paid once per Router pair instead of once per service. The price is the second hop for a target on another Router, and a replicated location table; the table is bounded by Node count, which is why it is affordable, and is the reason the earlier business-key binding replication is not coming back. Authority over where a player lives stays with the business code that decides it.

## 2. Nodes, attachment and the mesh

**RT-NODE-01** A Node identity is `(nodeId, nodeEpoch, serviceId)`. nodeId is a nonzero uint32, nodeEpoch a nonzero uint64 and serviceId a positive int32. Router IDs and service Node IDs share one namespace. Each Node serves exactly one service. nodeEpoch distinguishes process incarnations: a restarted process uses a new value, which must be distinct but need not be larger.

**RT-NODE-02** Attachment is bound to the connection. A service Node is attached to **at most one Router at a time**: the one it is connected to. It announces its identity there as soon as it sees the connection and again periodically, and every routed message it sends announces it too. A Router keeps the latest announcement per Node only while that Node is connected; a new incarnation replaces the old one. An announcement stops counting when its connection closes or the Node withdraws with the same epoch; an implementation that learns of closed connections only when a send fails MAY discard it then. A service that receives a delivery from a Router it is not using withdraws from that Router again, so a withdrawal overtaken by an earlier announcement still takes effect. An announcement is not a registration: it is not acknowledged or persisted and says nothing about service presence. A restarted Router learns its own Nodes again from their next announcements, and the other Routers from their next location refresh.

**RT-MESH-01** Every Router is connected to every other Router it relays through, and each pair has exactly one connection: **the Router with the larger ID initiates it**, so the Router with the smaller ID learns its peer from the inbound handshake. A Router MUST know the IDs of the Routers in the mesh and MUST treat a location message from any other Peer as invalid: a Node that is not a declared Router cannot inject locations. Router IDs are the application's configuration, like their addresses. A Router MUST NOT relay a message it received from another Router to a third Router, which makes the mesh loop-free without a hop count.

**RT-STATE-01** A Router MUST keep only two things, both bounded by the number of Nodes: the announcements of the service Nodes connected to it, and the locations other Routers reported. It MUST NOT keep a business-key binding table, a route cache for keys, a registration, a pending call, a sequence number or any message. An announcement on its own connection is authoritative and MUST win over a reported location for the same nodeId, because a directly connected Node is where it says it is.

**RT-STATE-02** A Router reports its own attachments to each connected Router as a **complete set** periodically, and as an immediate single-entry addition when a Node attaches and an immediate single-entry removal when one of its announcements is dropped. A complete set replaces everything that Router previously reported, so a Node that disappeared without a removal is forgotten by the next refresh; a removal applies only when both nodeId and nodeEpoch match. Reports are not acknowledged, carry no sequence number and are never retried: the next periodic complete set repairs any loss. A reported location is usable only while the connection to the Router that reported it is up; when that connection is gone, everything it reported MUST stop being usable, so a mesh link that is down makes the Nodes behind it unreachable rather than falsely addressable. Convergence after a Node attaches or moves is therefore bounded by one refresh period, and the immediate addition and removal make the common cases faster than that.

**RT-STATE-03** A routed message a Router receives from another Router MUST also locate its own sender on that Router, exactly as a service's routed message announces it where it is attached. This is what makes the second hop self-sufficient: a request's response needs the caller's location, and a report carrying it travels the same connection but not necessarily the same Slot, so without this rule a first call could be answered into a hole that the next refresh would have filled. A location learned this way is an ordinary reported location in every other respect, and a Node attached here is never displaced by one.

## 3. Addressing

**RT-ADDR-01** A routed message targets an exact nodeId, optionally with an exact nodeEpoch that the delivering Router checks. Dynamic addressing is resolved by the sender before sending; a Router never maps keys to Nodes. Player example: the service that owns player B records in business state that B is on Node 12; a sender looks that up and sends to Node 12, putting B's ID into the business identity or payload. If B moved, the sender's lookup decides where the message goes; the Router guarantees nothing about moved players.

**RT-ADDR-02** A service Node sends every routed message to the one Router it is connected to; there is no per-message Router choice and no sender-side warm-up. Messages with one routeKey to one target therefore keep their order while that connection and the target's location are unchanged; a change of either, including the target moving to another Router, does not preserve order across the change.

**RT-ADDR-03** A Router answers a Call with PEER_NOT_FOUND when it can see no location for the target, and the sender MUST report that error rather than resend: with one connection there is no second path to try, and the Router has already consulted the whole mesh it can see. PEER_NOT_FOUND therefore means "not attached anywhere this Router can reach", which includes a target behind a mesh link that is down. A Call that failed locally, for example on connection loss, may have been delivered and MUST NOT be resent.

## 4. Forwarding and call completion

**RT-DATA-01** A Router accepts a routed message only when its source Node is the direct RPC Peer it came from, or when it came from a declared Router in the mesh. It then resolves the target: a Node attached to itself is delivered to, addressed to that exact incarnation; a Node another Router reported is passed once to that Router, which delivers it; anything else fails per RT-DATA-03. A message that arrived from a Router is only ever delivered locally. Metadata, body, business identity, command, routeKey and the call ID survive both hops; the inner RPC frame passes byte for byte apart from the call ID. A service accepts routed messages only from the Router it is using and only for its own ID and epoch.

**RT-DATA-02** The caller's RPC Node owns a routed call's pending state and timeout; no Router creates a call or keeps a correlation. The caller's Router puts the caller's outer call ID into the forwarded request. The target replies to the Router that delivered the request, addressed to the caller's exact incarnation, and that response is routed by the caller's nodeId exactly like any other message: delivered at once when the caller is attached there, or passed once to the Router the caller is attached to. Because a service Node is attached to one Router, that resolution is unique and reaches the Router that holds the caller's pending call, which completes it with a native RPC response. No message carries the Router it came from. A response for an incarnation that is no longer attached, or whose caller's location is gone, is dropped. When the caller's own Router or its connection to it is lost, RPC fails the pending call; a late response then has nothing to complete.

**RT-DATA-03** A Call whose target has no usable location fails at once with RPC PEER_NOT_FOUND; a refused send, to an attached Node or to the next Router, fails it with UNAVAILABLE; an exception in the target's routed handler returns HANDLER_ERROR. A Notify has no one waiting and is dropped in those cases. Routers never buffer or retry business messages: a next hop whose write buffer is full refuses the message, and the write buffer of a mesh connection has to cover the bytes in flight between two Routers. ACCEPTED means first-hop admission only; Router provides no end-to-end receipt. A Router SHOULD count forwarded messages, messages passed to another Router, and every kind of drop (no location, send refused, response without its caller), so silent loss is observable. Remote errors, including a Router's own, go to the response handler; local RPC failures go to the failure handler.

## 5. Broadcast

**RT-BCAST-01** Broadcast is Notify-only. The sender sends one message to its Router. That Router delivers a copy to every Node of the service attached to itself, the sender included when it serves that service, each addressed to that Node's exact incarnation, and passes the broadcast once to every other connected Router, each of which delivers only to the Nodes attached to itself. A broadcast received from a Router is therefore never passed on again. Coverage is every Node of the service whose Router is reachable from the sender's Router; a Node behind a mesh link that is down misses it. There is no subscription table, aggregate result, replay or guaranteed delivery, and no deduplication: a Node attached to two Routers at once, which RT-NODE-02 forbids, would receive two copies.

## 6. Lifecycle and ownership

**RT-LIFE-01** Adding a Router needs no state transfer: the application connects it into the mesh, services it should carry are reconnected to it, and the Routers exchange locations within one refresh period. Removing a Router is the application's decision: the services attached to it are reconnected elsewhere and the mesh connections are dropped. A Router crash fails the calls in flight through it with RPC's connection-loss errors; the services attached to it are unreachable until the application reconnects them to another Router and that Router's locations propagate. A restarted service uses a new epoch, so traffic addressed to the old incarnation is refused or dropped.

**RT-LIFE-02** The application owns assembly and shutdown order: it closes routing, then RPC. Closing the service role stops its announcements and withdraws the Node from the Router it is using; closing a Router stops relaying, forgets every announcement and reported location, and reports the removal of its own attachments to the mesh if it still can. Routing creates no endpoint or business executor; the service role's periodic announcement and the Router role's periodic location refresh are its only background work. Accepted work has no cancellation, and a timeout leaves execution uncertain. Completion uses callbacks, not future-returning APIs.

## 7. Confirmed tradeoffs and validation

| Decision | Rationale | Reconsider when |
| --- | --- | --- |
| A service Node attached to one Router | `services + Router pairs` connections instead of `services × Routers`; one path per sender, so per-key order needs no Router choice rule | A service must survive its Router's loss without the application reconnecting it |
| Routers replicate locations, not business-key bindings | The table is bounded by Node count, so a complete refresh is one small frame; binding replication was unbounded and is not coming back | Node counts reach the frame or entry limit of one refresh |
| Complete periodic refresh plus immediate add/remove | Loss repairs itself without acknowledgement, sequence numbers or retry; the common cases do not wait for the period | Convergence must be bounded below one refresh period |
| At most two hops, never a third Router | Loop-free with no hop count and no routing decisions; a Router stays a forwarder | A mesh link is expected to fail while both Routers stay up |
| A location is unusable while its Router's connection is down | A broken mesh link reports PEER_NOT_FOUND instead of silently dropping into a hole | Multi-hop relay is accepted, with its loop prevention and reordering |
| Response routed by the caller's nodeId, no origin field | A caller is attached to one Router, so the ordinary resolution already reaches the Router holding its pending call | A caller can be attached in more than one place |
| Sender-side key resolution | Placement is business-owned; a Router can never follow a stale binding | Many senders need one shared key directory with guarantees the business store cannot give |
| The larger Router ID initiates the mesh connection | One connection per pair with no negotiation and no duplicate-connection race | RPC gains its own duplicate-connection resolution |
| Ordinary Handler on the existing Node | One identity, connection system and call-completion owner; assembly outside RPC | A concrete reusable RPC capability is missing |
