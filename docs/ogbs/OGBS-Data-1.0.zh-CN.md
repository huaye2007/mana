## 1. 职责与边界

**D-MODEL-01** Data 面向游戏进程中的可变状态，提供 Single、Group 与追加型 Log 三种 Repository。读取缓存未命中时同步加载；状态变更先在内存生效，显式 insert/update/delete 后异步批量写回。update 表示保存完整可变持久化状态，不是字段差异。同步加载在调用线程上访问存储，直到存储应答或驱动超时；因此读取只应在允许阻塞的执行上下文（例如 Runtime Route）中进行，不得在网络事件循环、RPC 回调或其他服务大量连接的线程上进行。并发加载的数量还受存储连接池约束：池满时加载在池的等待超时之后失败。

不提供 ORM Session、代理、自动 Dirty Tracking、实体快照、自动回滚、关系映射、自动生成主键、任意条件查询 DSL、分布式事务、跨进程缓存一致性或 Redis 二级缓存。特殊查询使用原生数据库访问层。

**D-OWN-01** 同一实体/组的业务修改顺序由应用串行化；容器线程安全不等于实体字段线程安全。应用必须保证后台读取实体字段与业务修改之间的可见性，以及需要的多字段一致性。引用进入待保存集合后仍可能继续改变，持久化观察的是编码时状态，不承诺 update 调用时的快照。实体中会被业务修改、同时被后台保存遍历的集合应使用线程安全集合（语言绑定给出具体类型）；不提供快照是为避免每次修改都复制实体的性能代价。

<a id="d-own-02"></a>

**D-OWN-02** 一个实体同一时刻只能由一个进程持有并写入（单写者），这是应用的放置职责。Data 的缓存、合并与串行保证都只在一个进程内成立：不提供跨进程的归属、租约、行版本或写入 fencing，存储也不会拒绝另一个进程的写入。两个进程同时持有同一实体时——例如玩家重连到另一个节点、故障切换、网络分区或运维误操作——两边各自加载、各自修改，并各自保存完整可变状态（D-SINGLE-02）；后保存的一方覆盖先保存的一方，先保存那一方的修改**静默丢失**，事后也无从发现。应用必须让实体只在一个进程上被修改，并在把它交给另一个进程之前，先让原进程保存（例如管理上下文中的 flush，D-FLUSH-01）并停止修改它。路由层的节点化身标识只区分消息投递的对象，不对存储做 fencing。需要框架层并发检测（例如乐观版本列）时，应作为新能力补充其冲突语义，不能把本条当作已提供。

## 2. 身份

**D-ID-01** Single 实体恰好一个持久化主键。Group 实体恰好一个持久化主键、至少一个组键字段及至少一个组内键字段。组键 + 组内键确定业务位置；后台变更始终按持久化主键合并、更新和删除，主键必须在整个实体存储范围唯一。

**D-ID-02** 实体加载或 insert 后，主键、组键、组内键均不得修改。实现不要求快照、setter 拦截或运行时身份比较；违反约定的结果不保证。不同实体类型的相同主键不合并。

**D-ID-03** 多字段组键及组内键必须声明稳定、不重复的顺序，不要求连续。单字段组内键使用原值；多字段组内键使用按该顺序的十进制整数/简单字符串，以 `:` 连接，不转义、不做长度编码。组件不得为 null；组合组内键的字符串不得含 `:`。组键保留各分量及类型，不转换为字符串。

### 2.1 三种身份不能混用

以玩家任务为例：

| 字段 | 示例 | 用途 |
| --- | --- | --- |
| 持久化主键 | id = 90001 | 数据库唯一行、待保存合并、更新和删除 |
| 组键 | roleId = 42 | 一次加载玩家 42 的整组任务 |
| 组内键 | taskId = 7 | 在该组 Map 中定位任务 |

另一个玩家也可以有 taskId = 7，但不能使用相同持久化主键 90001。GroupRepository 的 K 对应组内键，不是主键，也不是整个组键。复合组键的各分量保留类型和顺序；复合组内键的字符串规则见 D-ID-03，不能自行加入另一套编码方式。

身份不可变意味着“把任务从玩家 A 移到玩家 B”不能通过修改现存对象的 roleId 完成。业务需要显式删除旧身份、创建符合新身份的对象，并承担这两步之间不存在跨组原子事务的事实。

## 3. Single

**D-SINGLE-01** get 命中缓存返回同一实体引用；不存在返回空结果并可负缓存；存储失败必须同步报告加载错误，不得伪装为不存在或缓存为不存在。

**D-SINGLE-02** insert 声明新增，不得为检测存储是否存在而额外 SELECT。update 保存完整可变状态。两者立即更新缓存并记录变更，不等待数据库写入。Key 的缓存状态已知时，对已存在实体 insert、对已确认不存在的实体 update 必须同步拒绝且不登记任何变更；Key 未缓存时，存储冲突通过后台错误处理报告。getOrCreate 返回实体，不存在时在同一步中插入调用方提供的新实体。

**D-SINGLE-03** delete 不要求事先加载；接纳后缓存立即体现不存在，后续 get 不得在该缓存状态仍有效时加载尚未删除的旧行。删除已缓存为不存在的 Key 不登记任何变更。

## 4. Group

**D-GROUP-01** 按完整组键加载整组，以组内键构造 Map；零行表示已加载空组。加载失败、重复组内键、返回其他组的数据必须报告加载错误。

**D-GROUP-02** insert/update/delete/deleteGroup 遇到未缓存的组时，按 getGroup 相同方式加载，业务无需为写入而先加载。随后同步按组校验：组内键已存在时 insert、不存在时 update、update 换成另一主键的实体，均拒绝且不登记变更；delete 删除持有该组内键的实体（取其主键），组内键不存在时什么也不做。deleteGroup 对组内各实体记录主键 DELETE，再清空分组；已清空组仍为已加载空组。

**D-GROUP-03** getGroup 返回缓存分组的只读实时视图：能看到之后经 Repository 的变更，put/remove/clear 抛异常，结构变更只能经 Repository。应用可以遍历、读取实体和修改实体字段，字段变更必须显式 update 才有持久化保证。

### 4.1 操作前提与即时效果

| 操作 | 是否会同步加载数据库 | 接纳后的内存效果 | 后台持久化意图 |
| --- | --- | --- | --- |
| Single.get | 缓存未命中时会 | 缓存实体或不存在 | 无 |
| Single.getOrCreate | 缓存未命中时会 | 缓存实体或新建实体 | 新建时 INSERT |
| Single.insert / update | 不会 | 缓存指向传入对象 | INSERT / UPDATE，随后按合并表归并 |
| Single.delete | 不会 | 缓存体现不存在 | DELETE |
| Group.getGroup / get | 组未命中时加载整组 | 缓存真实 Map，包括空 Map | 无 |
| Group.insert / update | 组未命中时加载整组 | 写入对应组内位置 | 按实体主键登记变更 |
| Group.delete | 组未命中时加载整组 | 移除对应组内位置 | 按实体主键 DELETE |
| Group.deleteGroup | 组未命中时加载整组 | 清空分组，仍为已加载组 | 对当前组内各主键逐项 DELETE |
| Log.insert | 不会 | 追加到日志队列 | 后续按实际表 INSERT |

局部变量持有的视图始终对应取得它时的分组；空闲淘汰后，下一次经 Repository 的访问会加载新的分组，因此每次业务访问都应经 Repository 取得当前分组。

### 4.2 返回视图的使用约定

视图在每次加载分组时创建一次，读取不产生逐次包装开销。使用边界：

- 遍历、按组内键读取：可以。
- 修改实体可变字段：可以，但需显式 update，且遵守并发可见性约定。
- put/remove/clear：会抛异常，因为它们不会登记 INSERT 或 DELETE。
- 从外部线程同时修改实体：不因并发可读而获得许可。

deleteGroup 清空分组，因此持有其视图的业务会看到它变空。该操作只覆盖缓存组内已知实体，不等价于对数据库执行任意条件删除；绕过 Repository 写入的额外数据库行不在其保证内。

## 5. 缓存与保存生命周期

**D-CACHE-01** 存在未保存变更（包括为下一轮保留的可重试失败变更）的实体或分组 MUST NOT 被淘汰；只有已保存的干净条目在空闲到期后淘汰。淘汰从不强制或承担保存。经 Repository 访问会刷新空闲时间；直接访问此前返回的 Map/实体引用不会。应用应在每次业务访问时经 Repository 获取当前缓存对象。

**D-CACHE-03** 缓存条目受一个按 Repository 配置的上限约束。只有干净条目可以为满足该上限被淘汰——D-CACHE-01 依然成立——按最近最少使用优先，因此上限永远不会把未保存的工作挤出内存；当脏条目本身就达到这个数量时，计数会停在上限之上。容量淘汰在其他方面与空闲淘汰一致：在持久化流水线上、两轮之间执行，与同 Key 的修改原子进行；被淘汰的干净条目在下次访问时重新加载即可。它是突发之后由随后几轮逐步逼近的预算，不是写入瞬间强制生效的硬限制。把脏集合上限（D-WRITE-04）设得低于缓存上限，缓存上限才可达：缓存无法约束被未保存变更钉住的内存。

**D-CACHE-02** 脏条目始终留在缓存中，因此缓存未命中只会发生在没有待保存变更的 Key 上，从存储加载的就是当前数据，不会把未保存的修改回档。加载不查询待保存变更。淘汰对同一 Key 的待保存检查与该 Key 的修改原子互斥，并且只在没有已认领变更正在保存时进行。存储故障期间所有脏实体都留在内存中，直到保存成功或被丢弃；缓存有效时间仍应远大于正常写回延迟，以减少重复加载。

### 5.1 读取、修改与保存是三个时点

```text
T1 get 返回缓存 Entity
T2 业务修改字段并调用 update
T3 保存线程读取字段、编码并提交数据库
```

T2 表示持久化意图已登记。T3 可能看到 T2 之后的字段值；V1 没有“调用 update 时拍照”。多次 update 可以合并成一个后台更新，因此数据库不会必然观察到每一个中间状态。需要保留每次行为时应追加日志，而不是依赖状态更新次数。

加载失败与不存在必须分开：数据库返回零行可以形成负缓存；连接异常、解码失败或身份非法应报告加载错误。将这些失败缓存成不存在，可能诱使业务创建本不该创建的实体。

### 5.2 缓存过期与故障的组合

存储不可用期间，可重试的变更一直待保存，相应实体超过空闲时间也留在缓存中；之后读取得到的是同一内存实体，不会读到更旧的存储值。

最终被丢弃（见第 7 章）的变更使存储保持原状态，条目重新变为干净；过期后再读取得到的是存储状态。这类丢弃一定经过错误 Handler，应用可据此补救。

## 6. 写回与合并

**D-WRITE-01** 只有同一实体元数据、同一主键、尚未被保存流水线认领的变更合并。更新保留最新传入的实体引用；DELETE 只保留主键（Group 另保留实体引用以确定所属组）。已被认领的变更不再与新变更合并；仅当其因可重试失败放回时，才作为较旧的一方与新变更合并。

| 当前 | 新操作 | 结果 |
| --- | --- | --- |
| 无 | INSERT / UPDATE / DELETE | 新操作 |
| INSERT | UPDATE | INSERT |
| INSERT | DELETE | 无待保存变更 |
| UPDATE | UPDATE | UPDATE |
| UPDATE | DELETE | DELETE |
| DELETE | INSERT | DELETE_INSERT |
| DELETE | DELETE | DELETE |
| DELETE_INSERT | UPDATE | DELETE_INSERT |
| DELETE_INSERT | DELETE | DELETE |

其他组合必须同步拒绝，拒绝不得用新对象替换缓存。INSERT→DELETE 抵消基于调用方“确为新增”的声明，不探测已有数据库行。因可重试失败而放回的 INSERT 不再满足这一前提：失败的那次尝试可能已经写入了这一行。因此放回的 INSERT 与之后的 DELETE 合并为 DELETE 而不是抵消，与之后的 UPDATE 合并后仍保留这一性质；从未尝试保存过的 INSERT 照常抵消。

**D-WRITE-02** 任意时刻只有一条持久化流水线。每轮取一个有限边界——轮次到达某个实体类型时该类型已有的待保存变更——处理完毕后才开始下一轮；同一主键的较旧变更总先于较新变更执行。轮次运行期间登记的变更，以及边界之外的部分，都留给下一轮，因此持续生产不会把一轮拉长。配合 D-WRITE-04 的上限，一轮的工作量因此有界，生产者持续写入时轮次仍不断完成，进展从外部可见。每个实体类型内按 DELETE → DELETE_INSERT → INSERT → UPDATE 执行；各阶段按 batchSize 切分，每个批次在存储上原子生效，或按 D-ERROR-02 让部分生效的批次可以安全重试与拆分。实体类型间没有业务事务或原子性承诺。

**D-WRITE-03** 周期是目标启动间隔；上轮超过周期后可立即开始下一轮，不再额外等待完整周期。认领必须是原子的"条件移除"：认领之后才登记的变更必须留到下一轮，不能因认领与清理之间的竞争而丢失；实现不得依赖固定等待时间保证这一点。

**D-WRITE-04** 脏集合受一个配置上限约束，上限计的是所有状态 Repository 合计的不同待保存主键数。对已有待保存变更的主键的修改永远被接纳：它合并进那条变更（D-WRITE-01），不增加集合大小，所以上限不会拒绝对流水线已经欠着的实体的写入。会新增主键而集合已满的修改，等待某一轮腾出空间，等待有配置的上限；若仍没有空间则同步拒绝：不登记任何内容，缓存保持原样，调用方得到错误。被拒绝的修改从未被接纳，因此不报告给错误 Handler，不使 flush 或 close 失败，并与被丢弃的变更分开计数。实现不得为满足上限而丢弃已接纳的变更，也不得在组件停止接纳后继续挂住等待者：关闭时拒绝等待者。从持久化流水线内部登记的修改——来自存储适配器或错误 Handler 回调——等待的正是它自己所在的那一轮，因此立即拒绝，而不是拖住这一轮。上限是近似的——并发写入方，以及一次登记多条变更的调用（分组删除）都可能越过它——等待是有限的，因此持续写穿存储故障的应用最终看到的是拒绝，而不是不断增长的内存。

拒绝不是丢弃：没有任何内容离开内存，缓存仍然是调用前的内容。它无法撤销的是调用方在调用之前改到实体上的字段，这与非法序列被拒绝时的限制相同（§6.1）：此时内存领先于存储而没有待保存变更，条目变为可淘汰，之后重新加载会拿到存储中的状态。不能丢失这类修改的应用应重试写入或停住生产者；按写入速率设置上限，可以让这条路径只在存储故障时出现，而不是常态。

<a id="d-write-05"></a>

**D-WRITE-05** 一轮在同一轮里连续遇到两次可重试失败后，不再发起新的保存：没有尝试的变更与日志原样留在待保存集合，由下一轮处理。理由：存储不可用时每次调用都要等满同一个超时（例如连接池的获取超时）才失败，不停下的一轮会为每个批次各等一次，故障期间一轮的耗时随待保存数量线性增长，显式 flush 与 close 都被它拖住。只遇到一次不停，因为一次可重试失败通常是某一行的问题——锁等待超时、死锁——停在它上面会让被长期锁住的一行挡住它之后的全部变更；连续两次说明是存储本身。成功的保存与不可重试的失败都说明存储在应答，会清零这个计数。故障期间一轮因此最多花两次超时，"一轮的工作量有界"（D-WRITE-02）在时间上也成立。

### 6.1 合并示例与拒绝理由

下面的序列均假设同实体、同主键，且变更尚未被保存流水线认领：

```text
insert(A) → update(B)       => 一次 INSERT，使用 B 引用
insert(A) → delete(id)      => 无数据库操作
update(A) → update(B)       => 一次 UPDATE，使用 B 引用
update(A) → delete(id)      => 一次 DELETE，仅保留 id
delete(id) → insert(B)      => 一次 DELETE_INSERT，使用 B 引用
delete(id) → insert(B) → delete(id) => 一次 DELETE
```

重复 INSERT、UPDATE 后 INSERT、DELETE 后 UPDATE 等未列入合并表的序列被同步拒绝。这样调用方不会把“新增”“修改”“替换”混成隐式 save。拒绝不会用新参数替换缓存，但框架不能撤销业务在调用前已经直接改过的实体字段。

DELETE_INSERT 是删除后重建的持久化意图；各后端实现方式见第 8 章。它不是公开 Repository 方法，也不等于所有操作都有 upsert。

### 6.2 跨轮与跨批次

如果 insert 已被本轮认领，随后 delete 登记，两者不会抵消：先保存 INSERT，下一轮再执行 DELETE。即使数据库最终状态相同，也可能有两次真实 I/O、两次失败机会。

每个实体内的阶段顺序不代表不同实体之间有事务。举例：玩家金币 UPDATE 与奖励日志 INSERT 可以分别成功或失败；把它们放在同一 GameData 中不会获得原子提交。批次大小只控制每次交给 Mapper 的数量，不能推导出整轮事务边界。

## 7. 错误、重试与关闭

**D-ERROR-01** 后台状态及日志保存失败使用同一错误处理机制，携带错误码、实体/日志类型、操作、失败数据、原因、尝试次数。失败先由重试策略分类：可重试（瞬时故障，如连接中断、连接池超时、锁等待超时、死锁）的变更保留到下一轮再试，不限次数；默认策略只把这类瞬时故障视为可重试。连续的可重试失败会让一轮提前停下（D-WRITE-05）。

**D-ERROR-02** 不可重试的多行批次必须拆成单行重试，使其余行照常保存；不可重试的单行变更才被丢弃，交给错误 Handler 后继续后续工作，不能永久堵住保存。Handler/重试策略自身失败必须隔离并留有诊断。实体不回滚。存储适配必须保证重试与拆分既不会因部分成功产生重复行，也不会把自己先前写入的行报告为冲突：要么让每个批次原子生效（事务），要么在遇到已存在的主键时识别出那是自己先前一次结果未知的写入。不得用覆盖已存在的数据来换取幂等——那会把 D-SINGLE-02 要求报告的存储冲突变成静默覆盖。存储中不存在目标行的 UPDATE 视为不可重试失败，不得静默成功。

**D-ERROR-03** 正常路径不创建失败快照。Handler 同步借用被丢弃的实体引用；要异步保存失败信息，必须在回调返回前完成必要序列化/复制。默认 Handler 只记录诊断，不代替业务失败数据归档。

**D-CLOSE-01** close 是同步最终处理屏障：拒绝新的状态修改/日志接纳（包括按 D-WRITE-04 正在等待空间的写入方）、停止周期调度、等待进行中的保存，然后在关闭超时内反复执行轮次，直到没有已接纳的变更或日志，其间按刷盘周期重试被保留的变更。关闭超时是硬期限：期限过后不再发起任何保存，因此 close 在关闭超时加上期限时正在进行的那一次存储调用之内结束；零超时意味着不保存，直接进入下一步。期限到达、或存储在期限前一直失败时，仍未保存的每一条变更与日志都以丢弃报告给错误 Handler，附带实体，**不再尝试**；随后关闭自己的调度资源。应先停止业务接入再 close。

理由：关停预算的意义在于进程被强制终止之前把事情做完。存储故障时每次尝试都要等满存储超时才失败，期限之后若再逐批乃至逐行尝试，关闭耗时就与待保存数量成正比，进程会在报告任何东西之前被杀掉。把剩余变更在期限内交给错误 Handler，应用才来得及把它们转储到本地，再由人工或程序补写。

**D-CLOSE-02** 生命周期内发生过任何丢弃，关闭必须报告保存失败，不能仅因队列已清空而表示持久化成功。close 幂等；失败关闭重复调用仍报告失败。数据库驱动超时由应用配置，它决定期限到达时正在进行的那次调用最多还要多久。

**D-CLOSE-03** 进程崩溃可能丢失尚未写入数据库的数据，包括被保留的可重试变更。V1 不提供 WAL 或崩溃恢复。

### 7.1 从失败到最终处理

```text
执行当前 batch（原子）
  成功 → 继续
  失败且可重试 → 全部变更放回待保存集合，下一轮再试
  失败且不可重试：
       单行 → 丢弃，调用错误 Handler，记录失败
       多行 → 逐行执行；每行失败时同样先判断可重试
```

可重试的变更按实体主键去重，保留数量不超过脏实体数，不随更新次数增长。放回时与期间产生的新变更按合并表合并；若构成非法序列，保留较新的变更，较旧的变更作为不可重试丢弃并报告。

### 7.2 错误处理器的责任范围

错误 Handler 只接收被丢弃的变更，可以完成告警、同步序列化到外部失败存储（例如本地死信文件），或记录人工恢复需要的信息。回调收到的实体引用仍属于原可变对象；需要独立失败记录时，必须在回调返回前完成复制或序列化。Handler 自身抛异常不能阻塞后续保存。

### 7.3 关闭成功与持久化成功

close 先关闭修改接纳，再处理已接纳工作。数据库在关闭超时内恢复，保留的变更会被保存；未恢复时这些变更经错误 Handler 报告后丢弃，close 报告失败。此前发生过丢弃时，即使停机时队列为空，close 仍报告失败。

close 不负责停止上游 Runtime 或网络入口，也不关闭外部数据库客户端。应用应先停止业务生产、结束可能继续调用 Repository 的任务，再关闭 Data。进程被强制结束不具备正常 close 的处理保证。

### 7.4 显式 flush 与诊断

**D-FLUSH-01**：显式 flush 同步保存调用前已接纳的全部变更，保持 Data 开放。一轮是有界的（D-WRITE-02），因此 flush 会反复执行轮次，直到认领的数量不少于调用时待保存的数量。并发写入不保证包含在内；调用期间仍在写入的调用方，可能把自己之后的变更留在外面，所以稳定的屏障需要先停住写入方。存在历史丢弃，或本轮仍有被保留的可重试变更时，flush 报告失败（被保留的变更继续等待下一轮）。从持久化/错误回调递归 flush 应拒绝，避免死锁。驱动超时仍由应用配置。

**D-DIAG-01**：待处理变更、排队日志、被拒绝变更、最终失败批次和缓存数量为近似观察，不是持久化确认。待处理变更与缓存条目都有上限（D-WRITE-04、D-CACHE-03），因此计数贴着上限、以及被拒绝变更计数出现任何增长，都是生产快于存储的信号。Group 缓存数量指缓存组数，不是实体数。flush 成功只确认覆盖范围内的 mapper 操作，不是分布式事务，也不保护此前回写前的进程丢失。

修改实体仍需 update，返回的 Group 视图只读。不新增自动脏检测或不可变保存快照。关键业务可先暂停相关写入，在管理上下文执行 flush，普通游戏操作维持异步。验证见 [DataContractTest](../../game-data/src/test/java/cn/managame/data/DataContractTest.java)。

## 8. 存储适配语义

**D-STORE-01** JSON 字段提供默认编解码，不要求按字段手动注册类型。初始化绑定完整声明值/容器类型；对于构造初始化后非 null 的状态字段，还绑定兼容的具体实现类型。默认解码必须保留该实现以及泛型键、值和元素类型，不得静默替换为其他实现。初始值为 null 时按声明类型处理；存储 null 仍为 null。默认实现不支持的类型报告映射、编码或加载错误，应用可显式替换 codec。自定义 codec 决定具体表示，但结果必须可赋给字段。原始 JSON 文本字段保持直接传递。非法 JSON 是加载失败，不能当作不存在；写入编码失败进入保存失败流程。

例如声明 Map<Integer,Long> 并初始化为并发 Map 时，加载后仍为该并发 Map，键为 Integer、值为 Long，不需要手动类型注册表。状态映射时观察一次字段初始化结果，不从数据库内容猜测类型，也不把原型保留为业务状态。日志字段按声明类型处理，不构造日志对象；日志不加载，也不要求无参构造。具体 codec 配置与类构造支持边界由实现规范定义。

状态 Mapper 初始化时建立映射和必要存储结构。一个 Mapper 可以服务多个实体元数据；不得把不同实体的相同主键混合。

**D-STORE-02** Mapper 初始化时允许对存储结构做什么，是整个组件的一个选择，不是每个后端各自的选择：**create** 创建缺失结构并校验已有结构，**validate** 不发出任何结构语句，缺失的结构、以及装不下该映射写入内容的结构都要报告，**none** 不读任何目录、不做任何校验。默认是 create，因为首次部署没有可供校验的对象；结构由应用之外管理的数据库选择 validate，不允许应用读取目录的部署选择 none。校验比较类型声明的每一个尺寸，因此列宽小于映射写入所需时，由发现它的那次启动失败，而不是若干小时后由一次写入失败。create 只做增量——不删除、不收窄、不改类型——并容忍另一个进程在同一时刻应用同样的结构：存储因"结构已存在"而拒绝的语句不算失败，实现随后重新读取目录，校验另一个进程创建出来的结构，因此同一服务的多个实例可以同时启动。不属于"已存在"的拒绝（例如权限不足）仍让该次启动失败。none 下的不匹配首先表现为一次读或写失败。

MySQL：只有显式持久化字段参与 INSERT；UPDATE 保存全部可变字段，排除所有身份字段；DELETE 按主键。DELETE_INSERT 使用覆盖该批次删除与插入的小事务。create 下结构维护只建缺失表、补字段及显式索引，不自动删字段、改类型、删索引。类型冲突（包含声明长度不足）、主键不是被映射的那一个、同名但形状不同的索引，在两种会检查的模式下都让初始化失败；validate 下缺表、缺字段、缺显式索引同样让它失败。组键不会自动推导索引；Group 加载按全部组键做等值查询，create 与 validate 下若既没有声明、也没有已存在的索引以这些组键为前导列（顺序不限），初始化记录一条警告并给出应声明的索引，因为此时每次加载都扫描全表。

MongoDB：主键固定映射 `_id`。INSERT 为插入，从不替换已存储的文档：`_id` 已存在时，库中文档若与本次写入相同，或与此前一次失败的插入所发出的相同，就是自己的写入（后者替换为本次内容）；否则作为存储冲突报告，库中文档保持不变（D-SINGLE-02、D-ERROR-02）。多文档插入不是事务，失败的批次可能已存下其中一部分，正是这种识别让随后的重试与拆分把它们当作已保存。DELETE_INSERT 为带 upsert 的 Document replacement；UPDATE 为不 upsert 的 replacement，文档不存在时失败，与 MySQL UPDATE 未匹配行时一致；DELETE 使用主键集合。create 下仅创建缺失 collection 与显式升序索引，形状不同的同名索引让初始化失败；validate 下缺 collection 或缺索引让它失败。不提供 SQL 字段迁移。

## 9. 追加日志

**D-LOG-01** Log 只有 insert，进入追加队列，不缓存、不合并、不使用状态 EntityMapper、不要求状态主键。接纳后的日志及分表字段不得再修改。

**D-LOG-02** 本版日志使用 MySQL，复用 MysqlAccess。基础表由外部日志服务管理，组件不补字段或索引。结构模式为 create 时，分表不存在则在首次使用时以基础表为模板创建（`CREATE TABLE IF NOT EXISTS 分表 LIKE 基础表`）并重试一次插入；validate 与 none 下组件不发任何 DDL，分表须由部署预先建好，缺失的分表按普通保存失败处理——"在一处关掉 DDL"对运行期的分表同样成立。基础表不存在仍按普通保存失败处理。按实际物理表分组再批量 INSERT；每个周期取有限队列边界，持续生产不能阻塞状态保存；关闭期间排空全部已接纳日志。

**D-LOG-03** 分表支持 VALUE、DAY、MONTH、YEAR，最多一个分表字段；未标注则使用基础表。表名为基础名 + 下划线 + 后缀。时间分表使用明确时区的事件时间；单位、时区默认值及合法类型见 Java 标准。

**D-LOG-04** 日志存储与状态存储相互独立。实现不得由一方推导另一方：日志存储未配置属于配置错误，绝不构成把日志写入状态存储的理由；更换状态存储（包括换成另一类存储）也不得改变日志的写入位置。两者共用一个数据库时，必须分别为它们指定同一个存储。

### 9.1 日志完整流程

```text
构造日志并固定事件时间/分表值
→ insert 校验并接纳
→ 进入追加队列
→ 本轮取得有限处理边界
→ 按 batch 取出，按物理表分组
→ 执行每组 INSERT
→ 成功；可重试失败放回队尾；不可重试时拆分后丢弃并交给同一错误 Handler
```

两条字段完全相同的日志也不会合并。事件时间决定 DAY/MONTH/YEAR 分表，不能改为保存线程执行时的时间；跨日积压日志仍应进入原事件日期的表。分表在首次使用时按基础表创建；基础表缺失进入普通保存失败流程。

日志字段在 insert 返回后不可修改，包括不持久化但参与分表的字段。框架不提供日志快照，因此修改它们会同时影响内容与目标表，无法得到可靠的“接纳时事件记录”。

### 9.2 已确认取舍与扩展边界

| 选择 | 设计理由与后果 | 后续需要重新评估的条件 |
| --- | --- | --- |
| 显式 insert/update/delete | 操作意图明确，无代理或脏检测 | 自动追踪或字段级补丁需求 |
| 返回可变实体及真实组 Map | 业务直接操作内存；结构修改必须经 Repository | 要求隔离视图、不可变对象或快照 |
| 按 EntityMeta 与主键合并 | Mapper 可共享，不混淆不同实体类型 | 修改身份模型或引入动态实体映射 |
| 脏条目永不淘汰；只对干净 Key 读取存储 | 缓存淘汰不承担保存责任，也不会回档；无需叠加待保存变更 | 要求多进程强一致 |
| 瞬时失败保留重试，坏行拆分丢弃 | 数据库故障不丢数据；单个坏行不连累其他行，也不永久阻塞 | 引入持久失败队列或退避 |
| 连续两次瞬时失败即停止本轮；关停期限后不再保存，剩余变更一次性交给错误 Handler | 故障期间一轮与关停都只花常数次存储超时；关停预算内能把未保存的数据交出去 | 需要按存储分别判断可用性，或在关停时允许超出预算 |
| 脏集合有上限，写入方先等待再被拒绝 | 内存由设置决定而不是由结果决定；不会为腾空间丢弃已接纳的变更 | 需要持久溢出存储或按 Repository 分配预算 |
| 缓存有上限，只淘汰干净条目 | 一次大范围扫描不会把堆撑满整个空闲窗口 | 仅脏条目就超出预算 |
| 日志独立追加、复用错误机制 | 保留事件，不与状态合并 | 引入日志查询、其他日志后端 |
| 基础日志表由外部管理；分表按其 LIKE 创建 | 每日分表无需外部任务；表结构仍归外部 | 要求组件统一管理日志存储结构 |

当前没有承诺 WAL、崩溃恢复、跨表事务或多进程状态一致性；同一实体的单写者放置归应用负责（D-OWN-02）。积压保护指的是有界内存与拒绝（D-WRITE-04、D-CACHE-03），不是持久化的溢出存储。需要其中一项时，应明确补充行为、容量和恢复语义，不能只更换底层容器就宣布已支持。
