## 阅读说明

本规范定义游戏服务器通用网络组件的能力、职责和对上层可观察的行为，适用于不同开发语言和底层网络库。

本版已将“底层能力复用修订”完整合并到正文、兼容性检查清单及验收附录，替代此前 Draft 0.6 与独立修订说明的组合。本文是当前唯一的通用规范入口，无需再按两份文件的优先级解释冲突条款。

核心原则是提供统一的连接和用户处理契约，直接复用底层已有的连接、收发、串行执行、生命周期、扩展及配置能力；不强制增加第二套处理链、连接状态机、收发队列或关闭协调机制。同连接串行、消息保序和数据使用责任继续保留。

正文第 1～14 章为规范性内容。标注“待决”的说明及所有附录均不构成新增强制要求。文中的概念名称表示语义抽象，不要求实现采用相同的类型名、方法名或对象布局。

具体语言、第三方库类型、方法签名、默认数值和运行测试结果属于独立实现文档，不作为本规范的统一要求。本次合并不将附录 A 中剩余待决事项自动定稿，也不以某个实现已经通过测试代替标准兼容性判定。

# 1. 目标与范围

## 1.1 目标

GNS 为游戏服务器基础网络组件定义共同契约，使上层框架能够依赖稳定的连接、收发、事件处理、扩展和配置能力。

不同语言实现共享这些能力与行为保证，允许各自使用适合自身生态的接口形式及内部机制。

## 1.2 标准定义的内容

- 必须提供的核心抽象及其职责。
- 网络服务、连接建立与连接操作能力。
- 网络事件和消息交付语义。
- 同连接串行处理与消息顺序保证。
- 扩展接入、配置默认行为及用户覆盖能力。
- 声明兼容时需要满足的约束。

## 1.3 标准不定义的内容

GNS 不规定具体开发语言、第三方库、操作系统接口、IO 模型、调度机制或内存管理方式，也不统一具体 API 签名。

以下上层能力不属于核心标准：

- RPC 请求响应、服务发现与注册、节点管理、路由和负载均衡。
- 自动重连、节点切换和故障转移策略。
- 玩家身份、认证、会话、房间、匹配与业务调度。
- 业务心跳报文及超时处置策略。
- 消息序列化格式、协议编号、命令编号、请求编号及追踪协议。
- 数据库、缓存、分布式状态及服务治理。

上层可以通过 GNS 的接口和扩展能力实现这些功能，网络组件无需理解其业务含义。

## 1.4 组件契约与通信协议

遵守相同的组件契约，不等于采用相同的通信协议。

GNS 不统一线上消息格式、编解码规则或业务握手。不同实现之间需要通信时，由通信双方另行约定相应协议。此类协议约定不要求进入 GNS 核心标准。

# 2. 规范用语与术语

## 2.1 约束等级

| 用语 | 含义 |
|---|---|
| MUST | 兼容实现必须满足 |
| MUST NOT | 兼容实现禁止出现 |
| SHOULD | 强烈建议满足；存在合理限制时可以偏离，并说明原因 |
| MAY | 实现可以选择提供 |

可选能力一旦被实现声明支持，仍须满足正文中对该能力适用的强制要求。仅在说明性示例或待决问题中出现的设想不属于强制要求。

## 2.2 术语

| 术语 | 含义 |
|---|---|
| 实现 | 满足 GNS 契约的 game-network 组件 |
| 用户／上层 | 使用组件、实现处理接口或接入扩展的框架开发者及其代码 |
| 底层网络库 | 实现选择使用的第三方网络设施；不要求必须存在 |
| Connection | 面向持续通信的逻辑连接；适配对象可以在准备阶段创建，对上层的成功交付须满足协议就绪条件 |
| Message | 网络收发或处理过程中的数据对象，不限定具体类型 |
| write | 向 Connection 提交 Message 进入出站处理流程的逻辑操作 |
| NetworkHandler | 实现提供、由用户实现的标准网络事件处理接口 |
| 原生扩展 | 底层网络库自身提供的处理器、处理链或其他扩展能力 |
| 出站处理顺序 | 消息实际进入同一连接底层有序出站处理的顺序；不等同于不同调用上下文中 write 返回接受结果的时间先后 |
| 串行处理 | 同一连接的 NetworkHandler 处理不在不同执行上下文中并行；底层同步传播产生的嵌套按第 10.5 节处理 |
| 处理完成 | 本次 Handler 调用及通过其完成契约纳入的工作已经结束；包括正常结束或失败结束 |
| 关闭过程 | 从关闭请求到传输终止及资源清理的过程，可直接采用底层定义的边界，不要求组件另建原子生效点 |
| 标准事件交付 | game-network 将第 9.2 节事件交付到用户 NetworkHandler 的过程；不同于底层处理器之间的内部传播 |

“接口”在本规范中表示用户可实现的行为契约，不限定某种语言的接口语法。

# 3. 设计原则

## 3.1 实现独立

GNS 统一能力和行为，不统一内部实现机制。

实现 MAY 自行选择对象结构、第三方库、执行资源、同步或异步表达方式，以及配置表达形式。

实现 MUST 提供本规范约定的行为保证，不得要求用户依赖某一种特定的业务执行模型才能获得这些保证。

## 3.2 最小核心

必备核心抽象只有 NetworkServer、NetworkClient、Connection、NetworkHandler。ConnectionType 是连接协议类型的公共概念，不是第五个生命周期或资源管理对象。

处理链、地址对象、协议对象、编解码对象、配置对象和工厂等 MAY 作为实现提供的辅助抽象，但不因此成为 GNS 的必备核心对象。

## 3.3 上层无关

实现 MUST NOT 要求连接或消息具备特定的玩家、账户、节点、服务、请求或路由语义。

用户可以绑定或传递这些数据；组件仅负责提供相应网络能力。

## 3.4 复用与扩展

实现 MAY 复用底层库，也 MAY 自行提供网络处理设施。

存在底层原生扩展能力时，实现 MUST 提供相应接入方式，允许用户复用这些能力，具体要求见第 12 章。

标准不要求额外封装一条统一处理链，也不禁止实现提供自己的处理链。

## 3.5 基础保证的责任

标准要求的事件交付、同连接串行、消息保序和生命周期约束 MUST 由 game-network 在其声明支持的使用条件下提供。

实现 MAY 直接利用底层已有保证，不足之处由组件提供必要适配。MUST NOT 要求用户重新实现底层已有的基础分发、网络调度、加锁或排队，才能使用标准能力。

标准不要求为同义状态另行维护关闭标志、写入计数、互斥锁或收发队列，也不要求消除底层同步传播中的所有事件嵌套。复用边界见第 8～10 章。

用户接入的原生扩展必须遵守声明的事件传播、消息顺序和数据责任，见第 12.4 节。组件不负责补救用户主动吞掉必要事件、破坏原生节点或异步重排消息的行为；外部业务任务和共享业务状态仍由上层负责。

# 4. 核心模型

| 核心抽象 | 必备职责 |
|---|---|
| NetworkServer | 启动和停止网络服务，接受连接或提供声明支持的请求服务 |
| NetworkClient | 主动建立连接，并使连接建立失败可被调用方感知 |
| Connection | 提供统一的连接身份、类型、状态、write、关闭、属性及远端信息能力 |
| NetworkHandler | 让用户实现网络事件与消息处理逻辑 |

```text
NetworkServer ── 接受连接 ──┐
                           ├── Connection ── 网络事件交付 ── NetworkHandler
NetworkClient ── 主动建连 ──┘                                  用户实现
```

图示表示逻辑关系，不要求固定的内部调用链或对象持有关系。

NetworkServer 接受的长连接与 NetworkClient 主动建立的长连接 MUST 使用统一的 Connection 核心抽象和行为契约。

NetworkHandler MUST 提供。HandlerPipeline 不属于必备核心抽象。

HTTP 请求响应模型的适用范围见第 5.3 节。

# 5. 网络协议能力

## 5.1 当前范围

| 能力 | NetworkServer | NetworkClient | 成功建立后的上层模型 |
|---|---|---|---|
| TCP | SHOULD 支持 | 当前标准定义的长连接能力 | Connection |
| WS | SHOULD 支持 | 当前标准定义的长连接能力 | Connection |
| WSS | SHOULD 支持 | 当前标准定义的长连接能力 | Connection |
| HTTP 请求响应 | SHOULD 支持 | 当前版本不标准化 | 不要求采用 Connection 作为请求响应模型 |

实现 MAY 只支持部分协议。上表列出范围和建议程度，不表示所有协议对每个实现都属于必选能力。

实现 MUST 明确声明其支持的网络能力，使调用方能够区分 NetworkServer 与 NetworkClient 的实际支持范围。不得将未实现的能力表述为已支持。

**待决 A-10：** Server、Client 各自的最低协议支持门槛尚未统一。

## 5.2 长连接

对于声明支持的 TCP、WS、WSS 能力，连接成功建立后 MUST 使用 Connection 表示，并满足适用的连接、事件、顺序与配置契约。

WS 与 WSS 在 GNS 定义的 Connection 核心操作上 MUST 提供一致的行为语义；具体协议能力差异不由本条抹平。

## 5.3 HTTP

HTTP Request、Response 及对应处理接口不属于本版的必备核心抽象。

本规范不要求把 HTTP 请求强行映射成一个独立的 GNS Connection，也不要求 HTTP 请求处理采用 NetworkHandler。

同时提供 HTTP 和实时长连接处理时，实现 MUST 具备将二者处理资源隔离的能力。

本条要求可提供隔离能力，不要求默认启用某种隔离方式，也不规定资源划分的实现手段。

**待决 A-10：** 隔离能力的具体保证范围与可验证边界尚未统一；本条不承诺所有类型资源或整机负载完全互不影响。

## 5.4 后续协议扩展

实现 SHOULD 允许后续扩展网络能力。

本版不定义 UDP 的数据报模型、KCP 或 QUIC 的具体上层契约，也不要求将这些能力统一成 Connection。实现 MAY 作为扩展提供，并说明其行为。

# 6. NetworkServer

NetworkServer MUST 提供启动网络服务和停止网络服务的能力。

NetworkServer 停止之后 MUST NOT 再接受新的网络连接或新的网络请求。

NetworkServer MUST 能够关闭自身管理的现有网络资源。

立即关闭、等待在途处理、优雅退出及等待时间等策略 MAY 由实现提供和选择；其中可配置部分遵守第 13 章。

**待决 A-09：** 启动失败、部分启动成功、重复启动或停止，以及“停止完成”的可观察边界仍待定义。本章不默认要求停止操作同步完成，也不默认允许调用停止后立即宣称已完成。

---

# 7. NetworkClient

NetworkClient MUST 提供主动建立其声明支持的长连接的能力，并允许调用方为建连提供必要的目标信息。目标地址形式及配置入口由实现决定。

成功建立后 MUST 向上层提供 Connection。成功条件 MUST 包含所选协议所需的建立过程及握手；底层传输连接成功不能被直接当作尚未完成握手的上层协议连接成功。

连接建立失败时，调用方 MUST 能够得知失败，失败信息 SHOULD 提供原因。协议建立失败 MUST NOT 被表示为成功的 Connection，也 MUST NOT 为其伪造 Connected。Connected 处理本身失败的规则见第 9.3 节。

连接建立结果的表达方式由实现决定。实现 MAY 组合底层已有的连接结果、握手结果和用户初始化结果形成就绪通知，不要求自建连接尝试状态机，也不把就绪通知变成 Connection 的第二套关闭和收发管理。

自动重连、退避、重试次数、节点切换和故障转移策略不属于 GNS 核心要求；上层可以利用已有连接建立能力实现这些策略。

**待决 A-09：** NetworkClient 自身资源生命周期、取消未完成的连接尝试及资源释放完成的通用边界尚未统一。各实现 MUST 说明其当前行为，但不要求各语言采用相同的生命周期方法名或同步／异步形式。

# 8. Connection

## 8.1 定义

Connection 表示一条用于持续网络通信的逻辑连接。成功交付给上层前，必须完成声明的协议就绪过程。

实现 MAY 在底层连接准备阶段创建 Connection 适配对象，用于扩展配置等操作；对象已经存在、能够查询类型或底层传输已激活，不等于已经成功建连。实现 MUST 说明准备阶段可用的操作及其限制。

Connection MAY 直接委托底层连接的标识、状态、write、关闭、远端地址及属性能力。标准不要求复制底层状态或维护独立生命周期状态机，也不要求所有边界对应公开状态值。

连接可用性、协议就绪、底层传输结束和用户处理返回是不同边界；其交付关系见第 9.3 节。

## 8.2 标识

每个 Connection MUST 具有唯一标识。同一标识范围内的有效 Connection MUST NOT 同时具有相同标识。

标识的数据类型与生成方式由实现决定。标识范围是逻辑上的唯一性边界，不要求为此引入新的核心对象。

**待决 A-01：** 唯一性范围及关闭后标识复用条件仍未统一。本版不将未定义的范围解释为进程级或永久唯一，也不据此允许即时复用。

## 8.3 有效状态与可写状态

Connection MUST 提供查询当前是否有效以及是否可写的能力。状态查询 MUST 能够与 write、close 及 Handler 处理并发使用，不要求用户为查询自行同步。

实现 MAY 直接映射底层的连接状态与可写反馈，MUST 说明各项含义；传输激活、协议握手完成和允许继续排队不能混为一谈。查询只是某一时点的观察结果，不是后续操作的预留或成功保证。

关闭请求、实际传输终止和状态查询的变化可以遵循底层过程，不要求组件另建“close 一经调用，所有查询与操作立即原子切换”的状态。实现 MUST NOT 把已终止的底层传输宣称为仍可正常通信；可写反馈是否同时变化按声明的底层语义解释。

水位反馈与是否拒绝 write 可以不同：不可写不必然表示底层拒绝继续排队。实现 MUST 说明二者关系，不得将可写状态当作下一次 write 的接受预留。本版不要求额外提供统一的可写状态变化事件。

## 8.4 Connection write 与接受结果

Connection MUST 提供 write 能力，用于提交 Message 进入出站处理流程。消息类型由受支持的转换能力和上层约定决定。

write 是逻辑操作名称，不强制特定返回类型或同步表达。实现 MAY 直接委托底层的写入及提交／刷新能力，并 MUST 说明写入何时向底层提交；不要求用户另行实现普通网络写入调度。

write MUST 支持多个调用方并发提交，也 MUST 允许从 NetworkHandler 内部或外部调用。实现 MAY 直接复用底层的线程安全调用、调度与有序写入机制。不同调用上下文的业务先后关系不由接受结果自动建立，顺序范围见第 10.3 节。

实现 MUST 明确每次提交的接受语义及其结果入口；可以用返回值、完成结果或底层原生结果表达，不要求另建一套结果对象：

| 结果 | 含义 |
|---|---|
| Accepted | 消息已转交受支持的出站处理路径，由该路径按约定承担后续使用及释放责任 |
| Rejected | 消息尚未转交即被完整拒绝；本次提交没有输出，组件解除为检查本次提交而取得的临时持有，调用方保留消息责任 |

Accepted 不表示编码成功、完成实际写入、到达对端或被业务处理。消息一旦交给底层，即使底层立即或稍后报告失败，也属于接受后的写入失败；MUST NOT 追溯改报为上述 Rejected。原生结果若使用其他名称，实现 MUST 说明其与这两种语义的对应关系及数据责任。

实现可以在转交前检查连接或输入，但不要求预先识别所有不支持的消息类型、资源不足或关闭竞争；底层出站路径发现的问题可以通过原生写结果报告，见第 9.4 节。

write 与 close 并发时，MAY 直接采用底层调度、失败结果和释放规则，不要求组件增加原子接受点、关闭锁或写计数。调用前的状态观察与实际提交之间可以发生关闭；该次写入按实际是否已经转交以及底层结果处理。

write 的消息顺序见第 10.3 节；数据责任见第 11.5 节。

## 8.5 关闭

### 8.5.1 基本边界

Connection MUST 提供幂等的 close 能力，并允许其与 write、状态查询及 Handler 处理并发调用。

实现 MAY 直接请求底层关闭；重复 close 沿用原生幂等关闭过程，MUST NOT 重新建立连接或由组件重复生成生命周期通知。

关闭请求可以异步生效，其返回不表示底层资源、协议关闭、待写数据和用户回调均已处理完毕。实现 MUST 说明请求返回、传输终止和资源清理的可观察边界，不要求将它们合成为一个组件原子生效点。

关闭期间是否仍有原生读写、空闲、错误或断开通知，按底层协议处理器及事件传播规则执行。实现不要求额外拦截原生事件、建立缓存队列或延后所有同步断开通知，相关串行与嵌套规则见第 10.5 节。

### 8.5.2 默认关闭

实现 MUST 提供并说明默认关闭行为。默认行为 MAY 直接调用底层关闭能力，保留所配置协议处理器的关闭握手、刷新、待写数据处置及资源释放规则。

GNS 不强制绕过协议设施，不要求一律丢弃尚未实际写出的数据，也不承诺排空所有已接受写入。默认关闭是否尽力发送待写数据、等待协议关闭或立即终止，由实现声明的底层行为决定。

已经进入实际写入的数据可能部分或全部到达对端；关闭不承诺撤销、补发或业务确认。组件与用户扩展 MUST 按数据责任契约释放不再使用的资源，不因关闭或失败遗失清理责任。

因关闭取消或丢弃的待写数据，其结果 MAY 由原生写结果提供，不要求逐条重新生成 NetworkHandler Exception。

### 8.5.3 可选排空关闭

实现 MAY 额外声明排空此前已接受写入的关闭能力，也 MAY 直接复用底层提供的相应能力；默认协议关闭内部可能发生的刷新，不自动等同于这一额外承诺。

声明提供该能力时，MUST 明确待排空内容的纳入边界、新写入的处置及完成条件，并保持已建立的出站顺序。MUST 提供有限、可配置且有默认行为的等待上限；期限到达或无法继续写入时，终止排空并按声明规则关闭和释放剩余数据。

实现可以直接使用底层的截止边界、等待和完成结果，不要求复制一份排空集合或新建管理队列。排空不表示等待对端业务确认，也不自动等待上层外部任务。

### 8.5.4 关闭完成与重复请求

Disconnected 的交付以底层连接终止通知及声明的桥接关系为依据，见第 9.3 节。它不要求额外等待所有用户外部任务，也不意味着原生协议结果、错误回调或资源诊断从此不能发生。

实现 MUST 说明关闭完成的观察方式。重复请求不得由组件重新启动生命周期或无故延长其额外承诺的排空期限；原生关闭结果可以直接复用。

对端断开或不可恢复故障同样按底层终止流程和适用的错误契约处理，不能被组件掩盖为继续正常通信。

## 8.6 自定义属性

Connection MUST 支持用户附加自定义属性，组件不解释其业务含义。

不同 Connection 的属性绑定 MUST 隔离。修改 A 的绑定 MUST NOT 自动修改 B 的绑定；不要求对用户主动共享的可变对象深度复制。

Connection MUST 提供属性的查询、设置及显式移除能力。属性有效期 MAY 直接沿用底层连接对象的规则；实现 MUST 说明断开期间是否可读、关闭后是否自动清除，以及调用方保留连接对象时的属性持有行为。标准不要求在 Disconnected 返回后立即解除全部绑定，也不要求另建属性清理状态。

新连接 MUST NOT 自动继承已结束连接的属性。用户可按声明的接口显式移除不再需要的绑定；用户主动保留的属性对象不因连接终止或绑定移除而要求被立即销毁。

**待决 A-06：** 属性绑定的并发读改语义仍待明确；write、close 和状态查询的并发保证不自动扩展为属性对象内部状态的并发保证。

## 8.7 远端信息

Connection MUST 提供获取远端网络连接信息的能力。标准不固定 Address 类型、地址表示方式或返回结构。

**待决 A-12：** 最少应提供的信息及代理场景的远端含义尚未统一。

## 8.8 收发流控与底层行为

实现 MAY 直接复用底层网络库的收发队列、读取调度、写入缓冲、大小估算和流控机制及默认行为。GNS 不要求在其上再增加组件消息队列限额、字节预算、消息大小计算接口或超限断开策略。

实现 MUST 说明所采用机制的默认行为、配置入口和覆盖范围，区分“反馈可写状态”“暂停读取”“拒绝新写入”与“关闭连接”，不得把这些行为相互等同。底层没有提供硬性上限时，MUST NOT 宣称组件已限制待写数据总量。

实现 MUST 提供其支持的原生配置与扩展入口，用户未设置时可以沿用所选底层库的默认值或默认选择规则，不必复制底层选项或另外制造数值。显式配置的覆盖规则遵守第 13 章。

实现 MAY 提供额外的显式流控扩展，但这不是核心兼容性的前提。提供时 MUST 说明启用条件、计量范围、并发语义和超限行为；声明有限上限时，其覆盖范围内的实际队列必须被计入，不能通过转移内部队列虚报解除占用。

无论采用何种流控方式，write 的 Accepted／Rejected、并发顺序、错误报告与数据责任仍 MUST 遵守第 8.4、9.4、10、11 章。接受后的底层失败不得追溯改为 Rejected；未发生接受的拒绝不得遗留该次输出或持有。

入站同样不要求额外积压限额。实现 MUST 按第 9～10 章保持同一连接的串行交付与消息顺序，不要求用额外队列消除原生事件嵌套；必要的适配状态不等于对收发数据量的硬性保证。

## 8.9 连接类型

Connection MUST 提供连接类型查询，公共概念称为 ConnectionType，能够区分本版声明支持的 TCP、WS 和 WSS。各语言可以选择相应枚举或其他明确的类型表达形式，不统一枚举语法或对象布局。

类型描述该连接选定的协议，MUST 在对象创建时确定并保持不变；类型可查询不表示协议握手已经成功。WS 与 WSS 的区别属于连接类型信息，但不改变二者适用的 Connection 核心操作语义。

该要求不强制独立 HTTP 请求处理入口创建 Connection，也不为尚未标准化的协议预设类型成员。

# 9. NetworkHandler 与标准事件

## 9.1 用户接口

实现 MUST 提供由用户实现的 NetworkHandler 接口及接入方式，并负责标准事件交付。

标准不固定方法签名、注册形式或接口拆分。NetworkHandler 可以与原生扩展配合使用，不要求所有底层处理器都实现该接口。实现 MAY 安装一个原生桥接处理器，将底层连接映射为 Connection 并直接调用用户 NetworkHandler；不要求额外事件分发器或第二套处理链。

用户通过组件声明的完成契约完成当前事件，具体边界见第 10.5 节。

## 9.2 必备事件处理能力

实现 MUST 提供用户通过 NetworkHandler 处理下列事件的能力：

| 事件 | 语义 |
|---|---|
| Connected | 连接已建立并进入可交付给上层处理的生命周期 |
| Message | 原生或组件处理后继续交付给用户的数据对象 |
| Disconnected | 网络通信已终止，向用户交付一次连接终止通知 |
| Exception | 网络处理、用户处理或原生扩展中发生需要通知上层的错误 |
| ReadIdle | 配置时间内没有有效网络读取 |
| WriteIdle | 配置时间内没有有效网络写入 |
| AllIdle | 配置时间内既没有有效网络读取，也没有有效网络写入 |

事件交付 MUST 满足第 10 章。Exception 是逻辑事件名称，不要求某种语言的异常机制。

**待决 A-08：** 用户是否可以只实现关心的事件，以及 NetworkHandler 的必备出站接口范围仍待确定。

## 9.3 完整生命周期

在组件持续正常运行、用户处理能够结束且原生扩展遵守事件传播契约的条件下，成功进入业务交付的 Connection MUST 恰好交付一次 Connected，并在连接终止时最终恰好交付一次 Disconnected。

Connected MUST 对应所需协议已经就绪。正常的 Message 交付须在 Connected 处理成功后开始；同一连接不允许因组件调度而发生 Message 的并行处理或顺序重排。初始化失败或同步关闭产生的错误／生命周期嵌套，按第 10.5 节的原生串行规则处理。

Connected 处理本身失败时，实现 MUST 将本次初始化作为失败处置，请求关闭连接，并使对应建立结果或诊断入口可观察到原因，MUST NOT 再宣称用户初始化成功。该连接不要求补发业务 Disconnected；底层原生断开事件仍可继续传播。

成功进入业务交付后，Disconnected 通知用于处理连接终止。重复 close 不得使组件重复交付该通知。它 MAY 在原生关闭过程的同步调用中发生，不要求额外排队到当前回调返回之后。

Disconnected 之后，组件 MUST NOT 重新交付 Connected 或恢复业务 Message。该通知处理失败、原生写结果完成及后续清理错误仍可以按底层异常传播与诊断策略处理，不要求把 Disconnected 定义为禁止任何后续错误通知的绝对终点。

关闭与属性分别遵守第 8.5、8.6 节。实现不要求在 Disconnected 返回后立即清空属性，也不要求等待全部资源释放才通知断开。

上述保证不承诺进程被外部终止后仍有通知，也不要求中断永不完成的用户处理来制造通知。用户扩展主动拦截必要事件时的责任见第 12.4 节。

## 9.4 错误交付与失败终止

Exception 不等于必然关闭。能够被明确消费或恢复、且没有破坏连接与协议状态的错误 MAY 在处理后继续使用连接。

实现 MUST 使未被消费的处理错误和接受后的写入失败具备可观察的结果入口，并明确区分下列路径：

| 错误来源 | 允许的交付方式 |
|---|---|
| 建连、协议握手或用户初始化失败 | 对应的建立结果、初始化结果或服务端诊断入口 |
| 已转交出站路径后的编码、写入或关闭取消 | 底层原生写结果或实现提供的等价结果入口 |
| 原生管线向桥接层传播的异常、用户事件处理异常 | NetworkHandler Exception，或声明的原生异常传播与诊断路径 |

原生写结果可直接供上层观察，不要求每次写失败再生成一次 NetworkHandler Exception，也不统一逐条成功回调或消息关联标识。接受后的失败 MUST NOT 追溯改变接受语义或数据责任。若提供合并错误通知，实现 MUST 说明其覆盖范围，不得将其表述为逐条成功或送达证明。

不可恢复的协议或传输失败 MUST 按底层故障关闭规则或实现的明确策略终止通信；组件不得把不能继续通信的连接伪装为正常可用。默认 NetworkHandler 错误处理在未恢复错误时 MUST 请求关闭；用户显式配置的错误处理可以遵循所选底层机制，但 MUST 说明其恢复、传播或关闭责任。

Exception 或 Disconnected 的用户处理本身再次失败时，MAY 直接沿用底层的异常传播、日志、诊断或关闭行为，不要求为此构建独立终止状态机。实现 MUST 避免自己新增无限递归错误交付，并 MUST 说明最终错误的可观察入口。

继续传播的错误不等于恢复业务生命周期；后续资源清理仍按各自责任推进。原生扩展明确消费或拦截错误的边界见第 12.4 节。

## 9.5 空闲事件与心跳

实现 MUST 提供三种 Idle 事件能力，但不要求同时启用全部检测。三种事件可以通过一个带事件类型的处理入口表达，不要求拆成三个方法。具体默认值、默认是否启用及配置形式由实现说明，并遵守第 13 章。

上层业务心跳报文、响应及超时策略不属于 GNS 核心要求。该范围划分不排除底层协议自身需要的控制能力。

write 被接受仅表示进入出站处理流程，本身 MUST NOT 等同于已经发生有效网络写入。

关闭期间空闲检测的停止及事件传播 MAY 沿用底层生命周期，见第 8.5 节；不要求组件为 close 请求返回另建即时屏蔽机制。

**待决 A-07：** 有效读写的具体计量层级、计时起点、重复触发及重置规则仍待定义。

# 10. 串行、顺序与执行边界

## 10.1 同连接串行

同一 Connection 的 NetworkHandler 标准事件处理 MUST 串行，不得在不同执行上下文中同时并行执行。实现 MAY 直接利用底层的单连接串行执行保证，不要求统一线程、调度对象或 HandlerPipeline。

多个处理器共同处理该连接时，保证仍以 Connection 为范围，不得缩小为单个处理器各自不并发。普通 Message 的接收交付必须保持第 10.2 节的顺序。

底层同步传播中的事件嵌套遵守第 10.5 节，不等于允许并行处理，也不要求组件为避免所有重入另建队列。不同连接的并行及用户共享状态责任见第 10.4 节。

## 10.2 接收顺序

实现 MUST 声明原始数据经解析后交付 Message 的边界。原始输入中确定的先后关系及转换结果的逻辑顺序 MUST 在交付给 NetworkHandler 时保留，不能利用改变边界来掩盖内部重排。

```text
应交付消息：A → B → C
Handler 处理：A 完成 → B 完成 → C 完成
```

消息被扩展显式消费或因关闭丢弃后，剩余消息仍 MUST 保持相对顺序。

Connected 与 Disconnected 的边界见第 9.3 节；其他不同类别事件不要求按某个全局时间戳排序。

## 10.3 write 顺序保证

实现 MUST 复用或提供同一 Connection 的有序出站处理；组件自身不得重排底层已经建立顺序的应用输出。底层已有线程切换、排队与有序传输能力时，MAY 直接委托，不要求额外写任务、消息队列、序号分配或排序层。

同一串行发送上下文中按 A、B、C 顺序发起写入时，受支持的有序出站路径 MUST 保持其顺序。不同上下文交叉或并发调用的相对次序，按底层实际调度与出站处理顺序确定，不按各调用的开始时间或接受结果返回时间强行排序。

write 的 Accepted 只表示该次操作已被受理，不表示已经确定它与其他调用上下文中消息的业务先后关系。需要跨上下文表达业务依赖时，上层应在业务提交源组织先后；GNS 不把这种额外业务排序当作普通网络发送的必备步骤。

进入有序出站处理后，拆分输出 MUST 保持该消息内部的顺序；聚合、过滤或失败处置 MUST 保留剩余逻辑内容的相对顺序。原生扩展也须遵守所声明的有序处理契约，不能把任意重排配置自动视为兼容。

协议控制报文可按所支持协议处理，不得借此破坏应用消息的有序内容。具体控制协议不由 GNS 统一。

本节不承诺每条已接受消息最终送达，也不新增逐条确认机制。第 10.1～10.2 节的同连接回调串行与接收保序要求继续适用。

## 10.4 跨连接并行与共享

不同 Connection 的 NetworkHandler 处理 MAY 并行，不要求跨连接统一顺序。

实现 MAY 允许同一处理器实例用于多个连接，但 MUST 说明是否允许共享。共享不取消跨连接并行许可；用户主动共享的可变状态由用户按实现声明的契约保护，组件不自动保证业务状态互斥。

## 10.5 Handler 完成与新事件边界

一次 Handler 事件处理包括本次调用的执行，以及通过该接口完成契约明确纳入本次处理的工作。正常结束或失败结束都构成本次处理完成。

如果接口没有表达延后完成的能力，本次调用结束即为处理完成。实现 MAY 提供延后完成能力；提供时 MUST 明确如何观察完成或失败，并在完成前保持该连接后续消息的串行顺序。这是可选能力，不要求各语言使用同一种异步类型。

用户自行提交给外部执行机制、未纳入上述完成契约的业务任务，不属于当前事件处理范围。组件不会仅因为该任务由 Handler 发起，就自动等待其执行完毕。

Handler 内部调用 write、close 或接入原生处理逻辑是允许的。底层同步执行可能在当前调用栈中触发错误、断开或其他原生通知；实现 MAY 直接传播并桥接这些通知，不要求将所有新标准事件重新排队到当前 Handler 返回后，也不要求强制延后普通本地网络操作。

上述嵌套 MUST 保持在声明的串行执行契约内，不得据此启动并行的用户消息处理、重排入站消息或无限递归错误通知。实现 MUST 说明回调可否同步嵌套、延后完成的边界及原生扩展的责任。

write 的提交结果和 close 的请求受理 MUST 能够在不等待后续用户生命周期通知的情况下确定；不得迫使当前 Handler 同步等待一个只有自身返回后才能执行的任务。

用户主动等待依赖当前事件结束的外部结果属于上层逻辑问题，不要求组件破坏串行保证。数据跨回调或外部任务的有效期见第 11.5 节。

# 11. 消息处理能力

## 11.1 消息类型与边界

Message 可以表示原始数据、帧、协议对象或上层自定义对象。

实现 MUST 允许接入消息类型转换，并说明配置下交付给 NetworkHandler 的消息类型和边界。不要求任意对象未经转换即可直接写入网络。

编解码和通信双方格式约定由实现扩展及上层提供，GNS 不要求独立 Codec 核心对象。

## 11.2 零到多个输出

消息处理扩展 MUST 支持一次输入产生零个、一个或多个输出，以便完成解析、拆分、聚合、过滤及转换。

不要求每个 NetworkHandler 方法采用某种多返回值形式。输出顺序须满足第 10 章。

## 11.3 消费与后续处理

实现 MUST 允许用户接入消息消费、过滤和进一步处理。

消息被明确消费后，不再交付到其后续 Message 处理步骤；未被消费且经转换得到的输出，按已声明的边界交付给 NetworkHandler。

标准不要求统一传播方法、处理器上下文或处理链结构。

## 11.4 原生扩展

上述能力 MAY 直接由原生编解码或其他扩展机制提供。复用不免除 NetworkHandler 接口、事件交付和顺序保证。

原生扩展与标准事件的关系见第 12.4 节。

## 11.5 数据有效期与修改责任

### 11.5.1 write 输入

调用方提交 write 时，MUST 保证消息在接受结果确定前有效且不被其他操作修改。

Rejected 确定后，组件不再占用该消息的临时处理资源，调用方保留其使用和修改责任。

Accepted 确定后，组件 MUST 保证自身后续处理所需的数据持续有效，直到使用结束、被明确消费或按关闭／错误规则丢弃，并解除相应持有。

调用方 MUST NOT 再通过共享引用修改或使组件仍在使用的消息数据失效。若需要修改原数据或重复使用可变存储，应取得独立可用的数据，或采用实现明确提供的数据使用结束契约。

标准不要求复制，也不要求转移特定语言的物理所有权。实现可以使用独立数据、共享只读数据、保留引用或其他方式满足以上行为；不得要求调用方猜测底层何时不再使用数据。

数据使用结束不等于已送达对端，也不要求所有实现增加逐条写入成功通知。

### 11.5.2 接收数据

组件 MUST 保证交付给 NetworkHandler 的数据至少在当前事件处理完成之前有效，完成边界按第 10.5 节执行。

处理结束后，用户不得默认继续使用原有数据视图。实现 MAY 为特定数据类型提供更长有效期，但 MUST 明确说明。

实现 MUST 允许用户通过其支持的方式取得可在当前处理结束后继续使用的数据；方式可以是获得独立数据或显式延长有效期，不要求固定 API 或内存管理手段。

将数据交给外部业务任务前，用户 MUST 先满足延长有效期或取得独立数据的条件。否则外部任务不属于组件的默认数据有效期保证。

### 11.5.3 扩展和清理

消费、过滤、转换、拒绝、错误及关闭路径都 MUST 明确数据使用责任。组件与用户扩展按各自接入契约解除持有，不得因消息没有进入 NetworkHandler 就遗失清理责任。

用户主动保存的独立数据不因 Connection 关闭而必须销毁。组件对自身不再需要的数据的清理，与用户自行持有对象的生命周期相互区分。

# 12. 扩展能力

## 12.1 必备扩展入口

实现 MUST 提供用户扩展网络处理的能力，以支持第 11 章的消息处理及相关网络功能。

底层网络库已有原生处理器、处理链或其他扩展能力时，实现 MUST 提供接入这些原生能力的方式，允许用户复用其扩展。

原生扩展不要求被全部改写为 NetworkHandler；标准也不要求用户重新实现其事件传播流程。

实现 MUST 说明扩展的接入方式、作用范围以及与标准事件交付的关系。组件提供的接入方式 MUST 支持核心行为契约；用户配置的事件传播、异步执行和数据处理行为必须符合所声明的使用条件，具体责任见第 12.4 节。

本条不要求暴露底层全部内部对象或允许任意修改组件内部状态。

## 12.2 处理链可选

实现 MAY 提供 HandlerPipeline 或其他处理器组织形式。

GNS 不统一处理链对象、方向接口、遍历机制、上下文类型或动态增删接口。

提供自己的处理链、直接利用底层处理链及采用其他组织方式，都可以满足本规范。

“处理链可选”不表示可以封闭底层已有的原生扩展入口。

## 12.3 扩展与核心边界

扩展 MAY 提供核心标准之外的能力，具体实现自行说明其行为及适用条件。

扩展能力的存在不使其自动成为所有 GNS 实现都必须提供的功能。

**待决 A-11：** 是否有必要为可选处理链另行制定跨实现的扩展契约，包括动态修改生效时机，尚未确定。

## 12.4 原生扩展与标准事件交付

实现 MUST 说明原生扩展在编解码及标准事件交付之前或之后的作用位置、输入输出边界及数据责任，并允许用户通过受支持的原生机制选择适合的处理位置。具体插入、注册或动态修改形式由实现决定。

原生扩展 MAY 转换、聚合或消费应用消息。已消费消息不再产生该路径的后续 Message 交付；继续输出的消息必须遵守第 10 章。

桥接层遵守原生事件传播。用户扩展 MUST 按底层契约传播需要继续交付的生命周期、错误和协议事件；主动消费、拦截或移除必要处理节点，可能使后续 NetworkHandler 无法收到通知。组件不要求通过旁路补发被拦截的通知，也不要求保护一组用户不能修改的原生节点。

扩展内被明确处理或恢复的错误可以被消费；沿原生路径继续传播的错误，按第 9.4 节的桥接、原生结果或诊断契约处理。组件不得在自身适配中静默丢弃这些结果，但不替用户主动吞掉错误或结果承担补发责任。

用户扩展 MUST 保持需要的消息顺序及数据使用责任。主动异步重排、吞掉必要事件或破坏底层处理器契约的配置，不属于组件的默认保证范围；实现 MUST 说明这些使用条件。正常接入不要求用户重新实现组件的基础网络调度。

# 13. 配置能力

## 13.1 默认行为

实现 MUST 为其提供的可选网络配置项提供默认值或明确的默认选择规则。

用户未配置这些选项时，组件 MUST 采用所说明的默认行为，使用户无需逐项填写底层网络参数。

默认行为 MAY 由组件设定，也 MAY 采用底层库的默认行为；实现 MUST 说明实际采用的规则。

不同语言、底层库或运行环境不要求采用相同的具体数值。

## 13.2 用户覆盖

实现 MUST 为其支持的可配置选项提供用户选择与覆盖方式。

用户提供的受支持、有效的显式配置 MUST 优先于对应默认行为；未指定的选项仍采用默认行为。

被声明为可配置的参数 MUST NOT 固定为用户无法调整的内部取值。

## 13.3 必要输入

默认值要求适用于可选网络参数。

对于必须由用户提供且无法合理推导的部署输入，实现 MUST 说明其必要性；标准不要求为这类输入虚构默认值。

配置默认行为不等于标准要求所有部署都能在没有任何输入时启动。

## 13.4 配置形式与扩展

实现 MUST 提供接入其支持的底层网络配置选项的方式。

实现 MUST 说明受支持选项的含义、默认行为和适用范围；选项的使用仍须满足 GNS 核心契约。

实现 MAY 使用字段、配置对象、选项集合、配置文件、原生配置入口或其他形式。标准不规定或禁止任何一种表达方式。

标准不要求将底层所有配置逐一复制为 GNS 核心对象字段，也不枚举跨语言统一的底层选项集合。

配置能力应可扩展；新增实现专有选项不要求将其提升为新的 GNS 核心抽象。

收发流控可以沿用底层默认行为，具体声明与配置要求见第 8.8 节。可选排空关闭仍 MUST 遵守第 8.5 节的有限期限要求；这是所选关闭能力的完成契约，不要求额外收发队列限额。

**待决 A-13：** 非法配置、未知选项、多个配置来源的优先级及运行期间变更语义尚未统一。本版不默认承诺所有选项都支持动态修改。

# 14. 兼容性要求

## 14.1 判定原则

声明符合本草案的实现 MUST 满足正文所有适用的 MUST 和 MUST NOT 条款，并明确其协议支持范围。

兼容性不以接口名称、内部结构或特定网络库为依据。未提供统一 HandlerPipeline 不影响核心兼容性，已有原生扩展的接入要求仍然适用。

可选排空关闭仅对声明提供该能力的实现适用；默认关闭和收发流控行为声明要求对所有核心长连接实现适用。直接复用底层流控、不附加组件队列限额，不影响核心兼容性。

# 附录 A：设计决定与剩余待决（非规范性）

本附录保留原有编号以便追踪。A-02～A-05 已解决；A-06～A-08 部分解决；A-01、A-09～A-13 仍待讨论。已解决内容以正文为准，剩余建议不构成强制要求。

收发流控行为声明及原生扩展交付边界分别见第 8.8、12.4 节。第 8.8 节已按本版决定允许直接沿用底层默认流控，不再强制额外有限积压机制。

## A-01 连接标识范围与复用

**关联：** 第 8.2 节。  
**需要确定：** 唯一性覆盖单个 Server／Client、组件的一次运行，还是多个组件的共同范围？连接关闭后是否允许复用？如允许，如何避免延迟事件被误认成新连接？

**建议讨论：** 明确一个语言无关的唯一性范围，并讨论是否在该范围的一次生命周期内不复用标识。范围定义无需引入 Runtime 核心对象。

原稿“不得立即复用”缺少可验证的时长或状态边界。本版没有把这句话解释为允许即时复用，也没有直接升级成永久唯一；相关兼容性判定尚待补齐。

## A-02 连接生命周期与关闭——已解决

**正文：** 第 8.3、8.5、8.6、9.3 节。

正常原生传播下，成功进入业务交付的连接获得一次 Connected 和最终一次 Disconnected。Connected 初始化失败报告失败并关闭，不要求补发业务 Disconnected。断开通知不阻止原生后续错误传播，也不恢复业务交付。

close 直接采用底层关闭过程，不增加原子生效点、待写数据统一丢弃要求或禁止原生同步断开嵌套的机制。可选排空应说明边界和有限期限。属性允许沿用底层生命周期，不要求在 Disconnected 返回后立即清空。

## A-03 Handler 完成、嵌套与共享——已解决

**正文：** 第 10.1、10.4～10.5 节。

本次调用及通过接口完成契约纳入的工作结束，才算本次处理完成；用户另行提交的外部任务不自动纳入。延后完成是可选能力，不统一异步接口形式。

同连接处理不得并行，消息顺序得到保持；底层同步 write、close 或错误传播带来的事件嵌套可以直接沿用，不要求额外队列化。共享处理器是否允许由实现声明，其跨连接业务状态由上层负责。

## A-04 write 接受、并发顺序与后续失败——已解决

**正文：** 第 8.4、8.8、9.4、10.3 节。

write 可以并发提交并直接复用底层调度。相同串行发送上下文及底层已经建立的出站顺序得到保持，不额外保证跨上下文按接受结果返回时间排序，也不单独协调 write / close 的原子接受边界。

转交前的完整拒绝保留调用方数据责任；转交后的编码、写入或关闭取消属于原生写结果，不追溯改为拒绝。原生结果可以直接供上层观察，不要求每次失败再生成 Exception。转换、过滤和失败处置仍须保留剩余输出的逻辑相对顺序。

## A-05 消息边界与数据有效期——已解决

**正文：** 第 10.2、11.1、11.5 节。

实现声明消息边界，但必须保持原始输入中确定的顺序。write 接受后组件保证后续所需数据有效，调用方不能修改组件仍使用的共享数据。

接收数据至少有效至当前 Handler 处理完成；用户将数据交给外部任务前，需要取得独立数据或按实现契约延长有效期。具体复制、持有或释放手段由实现决定。

## A-06 Connection 操作并发与状态观察——部分解决

**已确定：** 第 8.3～8.5 节要求 write、close 及状态查询可以与 Handler 并发使用；查询不是预留，状态和关闭竞争可以直接采用底层语义，不要求关闭请求返回时立即原子切换全部状态。

**剩余待决：** 第 8.6 节中属性绑定的并发读、改、移除语义，以及读取远端信息的并发访问边界。公共写入保证不自动扩展到属性对象内部的可变业务状态。

## A-07 空闲事件计量——部分解决

**已确定：** write 接受本身不等于有效网络写入；空闲检测及关闭期间的传播可以直接采用底层规则，不需要组件额外即时屏蔽，见第 9.5 节。

**剩余待决：** 有效读写按原始数据活动、完整消息或上层消息计量？计时从何时开始？持续空闲如何重复通知，重置及协议控制活动如何计入？

**建议讨论：** 统一观测边界和计时规则，计时设施及默认数值继续由实现选择。

## A-08 NetworkHandler 事件覆盖与异常处置——部分解决

**已确定：** 第 9.4、12.4 节区分建连结果、原生写结果与管线异常。用户错误处理再次失败或 Disconnected 后的错误可以沿用底层传播和诊断，不要求额外终止状态机，也不允许组件新增无限递归交付。

**剩余待决：** 用户是否必须显式实现所有事件，还是允许默认处理？标准 NetworkHandler 是否包含必备出站接口，还是只通过原生扩展提供出站处理？

**建议讨论：** 保留全部标准事件能力，接口拆分由实现选择；再确定用户可省略的处理项，不改变本版原生错误结果和传播边界。

## A-09 Server 与 Client 生命周期

**关联：** 第 6、7 章。  
**需要确定：** 启动失败及部分监听成功如何报告？重复启动、停止如何处理？调用方怎样知道停止完成？Client 如何停止、取消尚未完成的连接尝试以及释放其管理的资源？

**建议讨论：** 定义操作结果与资源生命周期，不强制同步操作。立即关闭、等待在途处理等策略可以作为实现选项，但其结果需要可解释。

旧稿把连接建立能力描述为可选、同时又要求提供 NetworkClient 的矛盾已纠正；待决的是生命周期细节，不是是否提供主动建连能力。

## A-10 最低协议能力与 HTTP 隔离

**关联：** 第 5、14 章。  
**需要确定：** Server、Client 各自至少支持哪种或多少种长连接协议？是否允许两者支持不同协议集合？HTTP 隔离至少覆盖哪些资源或行为，如何检验？

**建议讨论：** 确定最低兼容门槛，并用可观察行为描述隔离边界。HTTP 隔离只在同时提供相关能力时适用，这不等于宣称所有共享资源均完全隔离。

## A-11 可选处理链契约

**关联：** 第 12 章。  
**需要确定：** 是否有实际需求统一可选处理链的方向、处理器位置、动态修改生效时机和在途事件处置？

**建议讨论：** 当前保留原生扩展接入能力，不恢复统一 Pipeline 强制要求。如需跨实现的处理链扩展标准，单独定义其适用范围，不能让选择其他扩展方式的实现承担无关要求。

## A-12 远端信息的最低语义

**关联：** 第 8.7 节。  
**需要确定：** 远端信息最少包含什么？它表示直接连接对端还是经过代理识别的原始端点？

**建议讨论：** 明确连接层可提供的信息边界，不统一 Address 类型，也不将网络地址等同于玩家或业务身份。

## A-13 配置校验、来源与生效时机

**关联：** 第 13 章。  
**需要确定：** 非法或未知配置如何报告？多个入口设置同一项时如何确定优先级？配置何时生效？哪些选项能在运行期间修改？

**建议讨论：** 避免静默忽略用户配置，说明选择来源及生效规则。用户有效配置覆盖默认行为已经确定，但多个显式来源之间的优先级尚未确定。

# 附录 B：说明性示例（非规范性）

本附录帮助理解标准意图，不要求实现采用其中的语言、类型或组织方式。示例不能增加正文没有规定的兼容性义务。

## B.1 复用底层原生扩展

假设底层库已有处理链或注册处理器的入口，实现可以直接开放该入口，让用户在编解码之前或之后添加日志、过滤或转换处理，再由一个适配处理器调用用户 NetworkHandler。

用户无需将所有原生处理器改写为 NetworkHandler，也无需重写底层已有的事件传播过程。选择其他扩展方式的实现同样可以满足标准，不需要为了统一外观再包一层 HandlerPipeline。

用户扩展如果主动消费某条消息，后续不再交付该消息；如果拦截了底层生命周期事件，也不能要求桥接层从另一条路径补发。扩展必须保持所需的传播、顺序和数据使用责任。

## B.2 配置的默认行为与覆盖

假设实现提供连接超时、缓冲和空闲检测选项，未设置时可以直接采用底层库的默认值或默认选择规则，用户通过公开的配置入口按需覆盖。

标准要求默认行为明确、受支持的有效选择能够生效，以及配置能力可以扩展；不要求复制底层全部选项为组件字段，也不规定各语言必须使用相同数值或配置结构。

必要的连接目标与可选调优参数不同。缺少不可推导的目标时，“提供默认行为”不意味着组件必须猜测远端地址。

## B.3 三种语言共享相同设计

Java、Go、Rust 实现可以采用各自生态中的接口、错误表达及扩展方式。

对使用者而言，三种实现都提供四个核心抽象，都允许实现 NetworkHandler，都保证同连接串行与消息保序，都支持扩展和可覆盖的默认配置。

这些共同保证不要求三种语言使用同一种处理链、同一个调度模型或相同的配置字段。

## B.4 串行保证与上层任务

假设收到 A、B 两条消息，NetworkHandler 依次处理 A、B。若处理 A 时将一项独立业务任务交给外部执行机制，该任务可以在 B 的处理之后才完成。

这不会自动改变 GNS 对 NetworkHandler 事件处理顺序的保证；外部任务完成顺序属于上层责任。

如果实现支持延后完成，用户可以按第 10.5 节的完成契约把工作纳入当前事件处理，后续消息交付遵守该完成边界；原生同步通知的嵌套仍按该节的声明处理。该契约不要求某种异步接口形式。将数据交给外部任务时，还应满足第 11.5 节的数据有效期要求。

# 附录 D：行为验收场景（非规范性）

这些场景将正文契约转化为可观察检查，不代表任何具体实现已经执行过测试。实现可以使用适合自身语言和底层设施的检查方式。

| 场景 | 操作与条件 | 应观察到的结果 | 正文 |
|---|---|---|---|
| 顺序接收 | 依次产生未被消费的 A、B、C | 普通消息按顺序串行处理，无跨执行上下文并行 | 10.1～10.2 |
| 延后完成 | 实现声明支持，A 尚未完成而 B 到达 | 依完成契约保持消息顺序，外部任务不会被自动纳入等待 | 10.5 |
| 同步事件嵌套 | Handler 内 write / close 立即产生原生错误或断开通知 | 允许声明的原生同步嵌套，不要求额外队列，不并行处理消息或无限递归错误 | 9.3～9.4、10.5 |
| 写入后失败 | 已转交的消息随后编码或实际写入失败 | 原生结果可观察失败，接受与数据责任不追溯改变，不要求再次生成 Exception | 8.4、9.4 |
| write 顺序 | 同一串行上下文顺序提交，另测跨上下文交叉提交 | 前者保序，后者符合原生调度声明，组件不重排底层已确定顺序 | 10.3 |
| 完整拒绝 | 转交前的有效检查拒绝一条消息 | 没有本次输出，解除检查临时持有，消息责任留给调用方 | 8.4、11.5 |
| 默认流控 | 对端读取得慢，观察写缓冲与可写状态 | 符合底层默认及配置，不把水位误报为拒绝或硬性上限 | 8.3、8.8 |
| 默认 close | 存在待处理或待写内容时请求关闭 | 符合原生协议及声明，最终资源释放，不强求全部发送或全部丢弃 | 8.5 |
| write 与 close 竞争 | 两项操作重叠 | 按实际转交及原生结果解释，转交后失败不误报为转交前拒绝，无需额外原子边界 | 8.4～8.5 |
| 可选排空超时 | 实现支持排空，纳入内容无法按时完成 | 到期按声明终止排空并关闭，不无限扩展范围或等待期限 | 8.5.3 |
| 生命周期 | 原生扩展正常传播，成功连接后重复关闭 | 成功交付的 Connected 和最终 Disconnected 各一次，不恢复业务消息 | 9.3、12.4 |
| 初始化失败 | 协议握手失败，或 Connected 用户初始化失败 | 结果或诊断报告失败并关闭，不伪造成功；用户初始化失败不强求业务 Disconnected | 7、9.3 |
| 连接类型 | 在 TCP / WS / WSS 准备、就绪及关闭阶段查询 | 类型明确且不变，不被当作握手成功证明 | 8.9 |
| 属性生命周期 | 设置属性、断开连接、继续持有对象或显式移除 | 隔离和有效期符合声明，不强求 Disconnected 返回后自动清空 | 8.6 |
| 接收数据长期使用 | 处理完成前取得独立数据或延长有效期，再交给外部任务 | 所取得数据按契约有效，不默认原临时视图永久有效 | 11.5 |
| 原生消费消息 | 扩展消费 A、继续输出 B，正常传播生命周期事件 | NetworkHandler 只收到 B，其余事件遵循原生传播 | 12.4 |
| 原生拦截事件 | 用户主动拦截必要生命周期或错误事件 | 后续桥接通知可能不可达，不要求旁路补发或将该配置纳入默认保证 | 12.4 |
| 用户错误处理失败 | Exception 或 Disconnected 处理抛出／返回失败 | 沿声明的原生异常或诊断路径可观察，不新增无限递归或独立终止状态机 | 9.4 |

验收应区分转交前拒绝、接受后失败、原生关闭处置、用户明确消费与真正的顺序错误，不能只用对端最终收到的消息数量代替全部契约检查。
