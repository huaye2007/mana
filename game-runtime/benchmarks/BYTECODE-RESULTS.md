# MethodHandle 与动态字节码实测 — 2026-09-12

本次纯调用测量中，生成字节码的耗时降低约 20%–71%；当前四参数路径的 32 B/次参数数组分配降至 0。
完整 Runtime 吞吐差值为 -7.2% 至 +4.6%，没有一致的提升，尚不能证明稳定的整体吞吐优势。
因此保留 MethodHandle 为生产实现；字节码生成器作为独立实验代码留在 benchmarks 内。

## 环境与对照

- Intel(R) Core(TM) Ultra 5 125H；Windows 11；Java HotSpot 25.0.3；JVM 可见 18 个逻辑处理器。
- 固定 256MiB 堆，G1；3 个独立 JVM/fork，每个 3 轮预热、5 轮测量；变体与场景顺序轮换。
- 微基准每轮 500ms；完整 Runtime 每轮 500,000 条消息。
- 完整 Runtime：64 个 Route、4 个平台工作线程、BALANCED、每批 32 条；
  4 个生产线程，每个最多 64 个未完成请求。
- 每组均绑定 32 个不同协议方法，分别令 1 个或 32 个协议活跃。四参数为 Id、Request、Extra、Extra，
  两个 Extra 必须复用同一次解析结果。
- 微基准总计 120 个测量样本，完整 Runtime 总计 120 个测量样本。
  完整 Runtime 测量阶段累计验证 60,000,000 条消息；加预热共 96,000,000 条。
- 单独的行为校验覆盖参数复用、隐藏路由源、异常传播和八种基本类型。微基准在计时前校验业务结果，每轮消费结果；完整 Runtime 每轮校验精确校验和与全部延迟记录。
- 两种变体在初始化时检查实际 invoker 类型，确保完整 Runtime 确实使用相应实现。

bound 使用生产 HandlerBinder/HandlerInvokers。bytecode 复制当前 Binder 到 target 内，
仅替换创建 CommandInvoker 的表达式；通过独立 JVM 的类路径优先装载。
参数规划、参数解析、协议入口、Route 调度、上下文和 Future 行为相同。
生产源文件和 JAR 不替换。

生成器通过 JDK Class-File API 生成真实 class 字节，再加载为 hidden class。
每个消息方法对应一个专用调用类，invoke 方法以 invokevirtual 直接调用具体 Handler，
不存在 MethodHandle.invokeExact 或反射 Method.invoke。
生成和实例化发生在计时之前。[反汇编样本](results/2026-09-12-bytecode-counterbalanced/generated-invoker.txt)

## 纯调用

统计先取各 fork 内五轮的中位数，再取三个 fork 中位数的中位数。
括号范围为 fork 中位数的最小值和最大值，不是置信区间。

| 参数数 | 活跃协议数 | MethodHandle ns/次（fork 范围） | 字节码 ns/次（fork 范围） | 耗时降低 | 分配 B/次：MH → 字节码 |
| --- | --- | --- | --- | --- | --- |
| 2 | 1 | 4.632（4.546–5.292） | 2.101（2.092–2.111） | 54.6% | 0 → 0 |
| 2 | 32 | 6.810（6.678–7.481） | 5.453（5.356–5.607） | 19.9% | 0 → 0 |
| 4 | 1 | 14.146（13.201–14.148） | 4.088（4.083–4.233） | 71.1% | 32 → 0 |
| 4 | 32 | 14.353（14.186–15.759） | 7.576（7.562–9.500） | 47.2% | 32 → 0 |

本次测得的“0 B/次”只针对预分配输入下的调用器，不代表完整消息零分配。
四参数数组消除是明确的局部收益；两参数路径原先就没有调用参数数组。
单协议与多协议之间的差异表明，需要用多方法分发场景评价代码生成，不能只测单一热方法。
这些时间结果包含同样的语义参数解析，但不包含路由准备与调度。

## 完整 Runtime

| 参数数 | 活跃协议数 | MethodHandle 百万条/秒（fork 范围） | 字节码 百万条/秒（fork 范围） | 吞吐差值 |
| --- | --- | --- | --- | --- |
| 2 | 1 | 2.814（2.742–2.852） | 2.941（2.452–2.957） | +4.5% |
| 2 | 32 | 3.029（2.928–3.072） | 2.956（2.696–3.064） | -2.4% |
| 4 | 1 | 3.026（2.905–3.043） | 2.809（2.680–2.843） | -7.2% |
| 4 | 32 | 2.831（2.695–3.105） | 2.962（2.905–2.974） | +4.6% |

| 参数数 | 活跃协议数 | MH P50 / P99 μs | 字节码 P50 / P99 μs |
| --- | --- | --- | --- |
| 2 | 1 | 25.1 / 73.9 | 25.8 / 71.8 |
| 2 | 32 | 27.2 / 75.0 | 25.7 / 71.9 |
| 4 | 1 | 26.2 / 70.2 | 24.9 / 69.1 |
| 4 | 32 | 26.3 / 74.4 | 26.0 / 69.8 |

吞吐覆盖提交到全部 RouteTask 完成。延迟从请求构造前计时，在 Handler 内记录，
包含排队、参数解析和执行到记录点的时间，不包含其后的 Future 完成通知。

各场景汇总 P99 均略低；两个单协议场景的独立 JVM 延迟范围仍有重叠。
两个 32 协议场景本轮的 P99 范围没有重叠，但样本数和合成负载的限制使其不足以承诺生产尾延迟改善。
完整吞吐三组的 fork 范围存在重叠；四参数单协议在本轮的字节码吞吐较低，
与另一个四参数场景的变化方向不同。逐轮数据也存在明显波动。
这里不能把 +4.6% 解释为确定的整体收益，也不能把 -7.2% 推广为必然退化。
本轮不声称达到统计显著性，亦不将这些合成负载数值作为生产容量。

## 对当前项目的判断

1. 预绑定 MethodHandle 已经是低开销方案，专用字节码仍有可测的局部优化空间。
2. 对四参数及以上方法，消除参数数组值得继续关注；这也可以通过扩展现有专用调用路径探索，
   无须直接把整个运行时切换到代码生成。
3. 本次完整调度中，局部加速没有等比例转化为吞吐提升；没有剖析数据，不能将其归因于某一个瓶颈。
4. 当前维持生产默认实现。若要接入字节码，应进一步测实际协议分布、真实 Handler，
   以及初始化耗时和类元数据成本。

这是自定义 JDK 诊断基准，不是 JMH。方法仅做轻量累加；未测生产 I/O、
开放到达率过载、启动成本或大量生成类的内存占用。生成器是面向本次可访问实例方法的实验原型，
没有完整替代生产系统的模块访问与类生命周期处理。
