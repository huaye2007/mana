# Binding invocation measurements — 2026-09-12

> 历史测量：以下样本采集于固定 RouteGroup 版本。后续 API 已迁移到游戏自定义 RouteType，基准源码也已迁移；之后又增加了执行域和实体批次轮转。这些旧数据不代表当前调度版本的重新测量。

本次改动把初始化逻辑拆为 HandlerMethodScanner、HandlerBinder 和 HandlerInvokers。扫描、校验、MethodHandle 适配只在构建 Runtime 时执行；消息调用使用预绑定调用器。项目没有自行生成 Handler 字节码；JVM 对 lambda 和 MethodHandle 的内部实现不属于这里的承诺。

## 环境与方法

- Intel Core Ultra 5 125H，Windows 11，JVM 可见 18 个逻辑处理器。
- Java HotSpot 25.0.3；固定 256 MiB 堆，G1。
- 每场景 3 个独立 JVM；每个 JVM 预热 3 轮、测量 5 轮。
- 表中结果先取每个 JVM 的轮次中位数，再取 3 个 JVM 的中位数；范围为各 JVM 中位数的最小值与最大值，并非置信区间。
- 自定义 JDK 基准，不是 JMH。完整说明和复现命令见 [基准说明](README.zh-CN.md)。

## 方法调用

每轮 250ms，8 个相同签名的不同接收对象/句柄轮流调用，1024 个预构造输入。direct 是普通 Java 调用；legacy 是基准保留的旧数组实现；bound 使用实际生产 HandlerInvokers。这里排除路由准备、请求构造、排队、Future 与线程调度。

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Command 2 参数 | 1.387 | 13.194 | 5.130 | 5.110–5.138 | 48 | 0 |
| Command 3 参数 | 1.752 | 15.304 | 6.344 | 6.320–6.374 | 64 | 0 |
| Command 4 参数 | 1.769 | 16.991 | 13.801 | 13.230–14.038 | 64 | 32 |
| Event 单参数 | 1.405 | 4.597 | 4.144 | 4.115–4.158 | 24 | 0 |
| Cron 无参数 | 0.743 | 4.167 | 3.211 | 3.204–3.222 | 16 | 0 |

所有 direct 场景的测量分配量为 0 B/次。4 参数场景包含一个重复语义参数；新实现只保留一个实参数组，重复值原位复用。1 参数 Command 的专用路径由功能测试覆盖，本表未测量该形状。

分配统计来自当前平台线程的 ThreadMXBean，显示至三位小数；JIT 消除的分配不会计入。这里的 0 B/次仅描述该调用基准，不意味着完整消息零分配，也不包含业务参数解析器自身可能产生的分配。

## 完整 Runtime 调度

最终负载每轮 1,000,000 条消息，64 个 Route、4 个生产线程，每个生产线程最多 64 个未完成请求。业务为简单累加并记录完成时刻，全部任务等待完成并校验业务结果。

| 入口 | 吞吐 消息/秒 | 各 JVM 吞吐范围 | P50 µs | P99 µs |
| --- | ---: | ---: | ---: | ---: |
| command | 1,186,303 | 902,387–1,277,650 | 1.8 | 57.2 |
| dispatch | 1,045,984 | 905,596–1,472,492 | 1.7 | 56.5 |

两者都使用当前 Runtime，不能据此推断此次修改的端到端加速比例。command 增加协议查找、身份解析及上下文创建；观测到的吞吐排序受调度、JIT 与机器负载影响，范围存在明显重叠，不能解释为 command 固有地比 dispatch 更快。

吞吐计时直到全部任务完成。延迟从请求构造/提交前，到业务 Handler 记录结果时为止，包含准入和排队，排除末尾 Future 完成通知。P50/P99 是各轮百分位再按上述方式取中位数，并非合并全部请求后的百分位。

原始数据：[逐轮样本与配置](results/2026-09-12-load.jsonl)、[汇总](results/2026-09-12-load-summary.json)。

## 工程判断

常用 Command 形状已移除调用器的参数数组，并降低此基准中的调用开销；4 个及更多参数走单数组通用路径。保留预绑定 MethodHandle，无需为当前结果引入自定义字节码生成器。是否继续优化应由真实业务剖析决定，尤其关注参数解析、上下文、队列、Future 和调度成本。

这是本地有界闭环负载，不是开放到达率、热点 Route、混合业务或生产容量测试。真实过载尾延迟可能显著不同；这些数字不能直接作为游戏服务器容量或延迟 SLO。
