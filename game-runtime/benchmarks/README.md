# Runtime invocation benchmarks

For the isolated MethodHandle versus dynamically generated bytecode comparison, see [comparison methodology and runner](BYTECODE-COMPARISON.md) and [measured results](BYTECODE-RESULTS.md).

[Runtime usage](../README.md) · [Recorded results](RESULTS.md)

This is a dependency-free diagnostic harness, compiled separately from the runtime JAR.
It compares normal Java calls, the previous array-based invocation path, and the current
pre-bound invokers. It also measures complete route dispatch and command execution.
It does not change production dispatch policies or add a runtime dependency. Historical results predate the current scheduler, reliable continuation and completion-notification changes; they are not measurements of this version.

## Run

With JDK 25 and PowerShell 7, from the repository root:

~~~powershell
mvn -pl game-runtime test
pwsh -File game-runtime/benchmarks/run.ps1
~~~

Default configuration: 3 independent JVM forks for each case; 3 warmup and 5 measurement
rounds; 250 ms per microbenchmark round; 8 binding targets; 256 MiB fixed heap with G1.
The script rotates variant order across forks.

~~~powershell
# Investigate a single target or a busy route separately.
pwsh -File game-runtime/benchmarks/run.ps1 -Mode micro -Targets 1
pwsh -File game-runtime/benchmarks/run.ps1 -Mode load -Routes 1
~~~

Each run replaces `game-runtime/target/benchmarks/results.jsonl` and `summary.json`.
The JSONL includes configuration, Java environment and every measurement sample.
The script fails on compilation/runtime errors or a workload checksum mismatch.
The benchmark source can also be compiled with javac and launched with java on another OS;
the runner uses the platform classpath separator.

## Invocation measurements

Cases cover Command methods with 2, 3 and 4 parameters, a one-parameter Event, and a
zero-parameter Cron. The four-parameter case repeats a semantic parameter, exercising
resolve-once behavior in the general fallback.

- `direct`: a normal Java method call through the same harness call interface.
- `legacy`: the earlier implementation retained in the benchmark, with two command
  arrays and one event/cron array. It is not shipped in the production runtime.
- `bound`: the actual production `HandlerInvokers` implementation.

Targets are distinct receiver/handle instances with the same method signature, selected
round-robin. Requests, semantic values and invocations are preallocated and varied over
1024 inputs. Routing and admission are excluded so that the invocation mechanism can
be compared independently. A checksum consumes business state and checks equivalent work.

Timing is sampled once per batch of 4096 calls. Allocation comes from the JDK
`ThreadMXBean` counter for the current platform thread. JIT-eliminated arrays therefore
do not count as allocations. Allocation numbers exclude route preparation, request
creation, queue entries, futures, scheduling and business-created objects. A zero result
here is not a claim of zero-allocation message processing.

## Complete route measurements

`dispatch` calls the business method through ordinary route dispatch. `command` adds
protocol lookup, route-identity resolution, command context and the current bound invoker.
Both use the current runtime; this is not a comparison against the previous scheduler. The command setup uses the current command-only registration form:

~~~java
var parameters = ParameterResolverRegistry.builder()
    .registerRouteSource(Id.class, inv -> new Id(((Envelope) inv.request()).route()))
    .build();
~~~

Defaults: 64 routes, 4 producer threads, at most 64 outstanding messages per producer,
1,000,000 messages per round, 3 warmup rounds and 5 measured rounds per fork. Every accepted
task is awaited and business checksums must match.

Throughput measures the whole batch until tasks complete. Latency measures from immediately
before allocating/submitting the request until the business handler records its result,
including admission, queue wait and execution up to that point. It excludes the final
future completion notification. The report shows P50/P99 for each round, then aggregates
round medians within each fork and medians across forks. It does not merge latency
histograms. Allocation is measured only in the isolated invocation cases, not across
virtual-thread execution.

## Interpretation

This is a bounded closed-loop load, not an open-loop offered-rate test. Tail latency under
overload can be very different. Empty business methods and a local machine cannot predict
real-game capacity or an SLO. The microbenchmark is a small custom diagnostic, not a JMH
suite: JVM compilation, shared-machine load and CPU scheduling can influence results.
Fork ranges are reported; they are not confidence intervals.

Compare allocation as well as time, and keep invocation results separate from full-route
results. Use these measurements to decide whether code generation is worth investigating,
then validate with representative game logic and production-like traffic before making
capacity claims.
